# 产品需求文档：微信个人 AI 陪伴与生活助理 Phase 1

## 1. 产品定位

本项目 Phase 1 旨在提供一个低门槛、可多人使用的个人 AI 陪伴与生活助理服务。

技术上复用 OpenClaw 和官方 `openclaw-weixin` 的微信连接能力，但不依赖 OpenClaw 原生共享的 `soul.md` 和长期记忆来承载产品体验。AI4ALL Backend 负责每个接入微信账号的 Soul、会话、记忆、配置和 LLM 调用。

目标模型是：

```text
一个 OpenClaw 实例
-> 多个个人微信账号接入
-> 每个微信账号拥有自己的 AI bot 会话
-> Backend 按账号隔离 Soul、上下文、记忆和配置
```

当前不采用“一个服务微信号服务多个外部用户”的客服号模型，也不做群聊 bot。

与偏工作效率的通用 AI 产品不同，Phase 1 更聚焦：

- 情感陪伴与日常闲聊
- 生活建议与轻量事务辅助
- 有稳定人设和表达风格的长期互动
- 文本与语音输入并存的自然交流体验
- 多个接入账号共享后端资源，但各自拥有独立上下文与记忆

## 2. 目标用户

### 2.1 C 端用户

希望通过自己的微信账号获得个人 AI 陪伴与生活助理能力的普通用户。

典型需求：

- 希望有一个随时可以聊天、回应自然的 AI 陪伴对象
- 希望通过微信文字或语音获得生活建议与轻量事务辅助
- 希望 AI 能记住近期对话上下文，而不是每次都从零开始
- 希望不需要自己理解模型、API Key、服务器或 OpenClaw 配置

### 2.2 管理者

负责部署、维护和运营该服务的人。

典型需求：

- 一个 OpenClaw 实例可承载多个个人微信账号接入
- 多个账号共享一套 LLM 与 ASR 资源
- 控制 API 成本和账号使用频率
- 保证不同账号之间的 Soul、会话、记忆、用量统计相互隔离
- 能观察系统运行状态，排查失败消息和异常账号

## 3. Phase 1 范围

### 3.1 必须实现

- 一个 OpenClaw 实例连接多个个人微信账号
- 支持私聊文本消息
- 支持私聊语音输入，并转换为文本后进入统一对话链路
- 支持多账号同时使用同一套后端服务
- 基于微信账号级 `account_id` 隔离对话上下文和历史记忆
- 支持每个账号独立默认 AI 人设
- 支持短期上下文记忆，保障多轮对话连贯
- 支持基础限流和每日用量控制
- 支持 LLM 与 ASR 调用失败时的友好降级回复
- 记录必要日志，便于追踪消息处理、模型调用、失败原因和用量

### 3.2 暂不实现

- 一个公共微信号服务多个外部用户
- 群聊 bot
- 图片理解和图片生成
- 文件处理
- RAG 知识库
- 多 Agent 编排
- 用户自定义复杂角色市场
- 支付、会员、套餐系统
- 完整管理后台 UI
- 流式输出和微信端打字机效果
- 长期记忆总结、画像沉淀和跨会话复杂记忆

## 4. 核心用户流程

### 4.1 首次接入

1. 用户或运营人员将一个微信账号连接到 OpenClaw。
2. OpenClaw 通过官方微信插件保持该账号在线。
3. 用户在微信中与自己的 bot 会话发送第一条文本或语音消息。
4. Bridge 将消息和账号上下文转发到 AI4ALL Backend。
5. Backend 识别 `account_id`，创建账号记录和默认会话。
6. Backend 注入该账号的默认 Soul，调用 LLM 生成回复。
7. 回复通过 OpenClaw 回到微信。

### 4.2 文本对话

1. 用户发送文本消息。
2. 系统完成消息去重、限流检查和上下文读取。
3. 系统组装 Prompt：账号 Soul + 近期历史 + 当前输入。
4. 系统调用 LLM。
5. 系统保存用户消息和 AI 回复。
6. 系统按发送策略回复用户。

### 4.3 语音对话

1. 用户发送语音消息。
2. 系统从 OpenClaw 或微信接入层获取语音文件或媒体引用。
3. 系统调用 ASR 将语音转为文本。
4. 系统将识别文本进入和文本消息相同的对话链路。
5. 如果 ASR 失败，系统回复用户“这条语音暂时没听清，可以再发一次或改用文字”一类提示。

### 4.4 限流或额度不足

1. 用户触发每日次数、短时间频率或 token 预算限制。
2. 系统不再调用 LLM 或 ASR。
3. 系统回复明确但不生硬的提示，例如“今天聊得有点多了，我晚些时候再继续陪你。”

## 5. 功能需求

### 5.1 微信接入

- 支持多个微信账号连接到同一个 OpenClaw 实例
- 接收私聊文本消息
- 接收私聊语音消息
- 获取微信账号级唯一标识
- 获取消息唯一标识，用于去重
- 支持向当前会话发送文本回复
- 记录原始事件，便于排查协议问题

### 5.2 账号与会话

- 根据微信账号级 `account_id` 自动创建账号记录
- 每个账号默认拥有一个主会话
- Phase 1 不提供用户主动切换会话能力
- 不同账号的历史消息、上下文和用量统计必须逻辑隔离

### 5.3 AI 人设

- 系统内置一个默认 Soul
- 每个账号可以覆盖默认 Soul 或风格
- Soul 以文本配置形式保存
- 默认风格应偏陪伴、自然、生活化，避免工具客服感
- 不向用户暴露底层 Prompt
- 后端设计上允许后续扩展多 Soul，但 Phase 1 不做完整角色市场

### 5.4 记忆与上下文

- 保存用户消息和 AI 回复
- 每次请求拉取最近 N 轮对话
- 根据 token 上限裁剪上下文
- Phase 1 只做短期滑动窗口记忆
- 不做长期总结记忆和用户画像

### 5.5 文本生成

- 支持配置 LLM Provider、模型名、API Key、超时、最大 token
- 支持调用失败、超时、限额不足时的降级回复
- 支持记录输入 token、输出 token、耗时和错误码

### 5.6 语音识别

- 支持配置 ASR Provider、模型名、API Key 和超时
- 支持语音文件下载或读取
- 支持识别结果进入统一文本对话链路
- 支持 ASR 失败时的用户提示和日志记录

### 5.7 用量与风控

- 按账号限制短时间请求频率
- 按账号限制每日交互次数
- 按账号限制单次上下文最大 token
- 支持简单黑名单
- 避免秒级高频回复和重复发送
- 对异常失败进行退避或熔断

### 5.8 日志与观测

- 记录每条入站消息处理状态
- 记录 LLM 和 ASR 调用耗时、结果、错误
- 记录账号级每日使用量
- 记录发送成功或失败状态
- 日志中避免保存明文密钥

## 6. 非功能需求

- 稳定性：单个账号请求失败不能影响其他账号。
- 隔离性：不同账号之间不得混用 Soul、上下文或历史消息。
- 可恢复性：服务重启后账号历史和用量统计不丢失。
- 可扩展性：后续可接入 RAG、更多 Soul、管理后台、付费系统。
- 成本可控：所有 LLM 与 ASR 调用必须经过限流和预算控制。
- 响应体验：文本消息常规回复目标在 5-20 秒内完成，语音消息允许更长处理时间。

## 7. 验收标准

- 至少 2 个不同微信账号可以同时连接同一个 OpenClaw 实例。
- 两个账号都可以通过 AI4ALL Backend 得到回复。
- 不同账号连续对话时，上下文不会串线。
- 账号 A 提到的信息不会出现在账号 B 的回复中。
- 不同账号可以配置不同 Soul 或回复风格。
- 文本消息可以完成至少 5 轮连续对话。
- 语音消息可以被识别并得到 AI 回复。
- 达到限流阈值后，系统不会继续消耗 LLM 或 ASR 额度。
- LLM 或 ASR 故障时，用户能收到可理解的失败提示。
- 管理者可以通过日志追踪一条消息从接收到回复的完整链路。

## 8. 待确认问题

- OpenClaw 多账号同时在线已完成本地验证；后续仍需观察长时间运行稳定性。
- Bridge 当前从 OpenClaw `sessionKey` 解析稳定微信账号级 `account_id`。
- OpenClaw 传递语音消息时提供的是媒体 URL、文件 ID，还是本地文件路径。
- 首版是否只允许白名单账号使用，还是扫码后默认开放。
- 默认每日交互次数和 token 上限是多少。
- 默认 Soul 的具体人设、语气和边界。
- 首版 ASR Provider 选择。
