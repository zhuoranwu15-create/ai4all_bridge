# 产品需求文档：微信个人 AI 陪伴与生活助理 Phase 1

## 1. 产品定位

本项目 Phase 1 旨在提供一个低门槛、免部署、可多人使用的个人 AI 陪伴与生活助理服务。

用户通过微信扫码或添加指定微信号即可开始使用，无需理解模型、API Key、服务器、OpenClaw 配置等技术细节。系统后端复用一套类 OpenClaw 架构能力，为多个用户提供相互隔离的 AI 对话体验。

与偏工作效率的通用 AI 产品不同，Phase 1 更聚焦：

- 情感陪伴与日常闲聊
- 生活建议与轻量事务辅助
- 有稳定人设和表达风格的长期互动
- 文本与语音输入并存的自然交流体验
- 多用户共享后端资源，但各自拥有独立上下文与记忆

## 2. 目标用户

### 2.1 C 端用户

普通微信用户，不具备技术部署能力，也不希望学习复杂 AI 工具配置。

典型需求：

- 希望有一个随时可以聊天、回应自然的 AI 陪伴对象
- 希望通过微信文字或语音获得生活建议与轻量事务辅助
- 希望 AI 能记住近期对话上下文，而不是每次都从零开始
- 希望无需下载新 App、无需注册复杂账号即可使用

### 2.2 管理者

负责部署、维护和运营该服务的人。

典型需求：

- 多个用户共享一套 LLM 与 ASR 资源
- 控制 API 成本和用户使用频率
- 保证不同用户之间的会话、记忆、用量统计相互隔离
- 能观察系统运行状态，排查失败消息和异常用户

## 3. Phase 1 范围

### 3.1 必须实现

- 微信扫码或添加指定账号后可发起对话
- 支持私聊文本消息
- 支持私聊语音输入，并转换为文本后进入统一对话链路
- 支持多用户同时使用同一套后端服务
- 基于用户 ID 隔离对话上下文和历史记忆
- 支持默认 AI 人设，具备稳定的陪伴式表达风格
- 支持短期上下文记忆，保障多轮对话连贯
- 支持基础限流和每日用量控制
- 支持 LLM 与 ASR 调用失败时的友好降级回复
- 记录必要日志，便于追踪消息处理、模型调用、失败原因和用量

### 3.2 暂不实现

- 群聊场景
- 图片理解和图片生成
- 文件处理
- RAG 知识库
- 多 Agent 编排
- 用户自定义复杂角色市场
- 支付、会员、套餐系统
- 管理后台 UI
- 流式输出和微信端打字机效果
- 长期记忆总结、画像沉淀和跨会话复杂记忆

## 4. 核心用户流程

### 4.1 首次使用

1. 用户扫码或添加指定微信号。
2. 用户发送第一条文本或语音消息。
3. 系统识别用户 ID，创建用户记录和默认会话。
4. 系统注入默认人设，调用 LLM 生成回复。
5. 系统将回复通过微信发送给用户。

### 4.2 文本对话

1. 用户发送文本消息。
2. 系统完成消息去重、限流检查和上下文读取。
3. 系统组装 Prompt：默认人设 + 近期历史 + 当前输入。
4. 系统调用 LLM。
5. 系统保存用户消息和 AI 回复。
6. 系统按发送策略回复用户。

### 4.3 语音对话

1. 用户发送语音消息。
2. 系统从 OpenClaw 或微信接入层获取语音文件或媒体引用。
3. 系统调用 ASR 将语音转为文本。
4. 系统将识别文本进入和文本消息相同的对话链路。
5. 如果 ASR 失败，系统回复用户“这条语音暂时没听清，可以再发一次或改用文字”一类提示。

### 4.4 限流或额度不足

1. 用户触发每日次数、短时间频率或 token 预算限制。
2. 系统不再调用 LLM 或 ASR。
3. 系统回复明确但不生硬的提示，例如“今天聊得有点多了，我晚些时候再继续陪你。”

## 5. 功能需求

### 5.1 微信接入

- 接收私聊文本消息
- 接收私聊语音消息
- 获取用户唯一标识
- 获取消息唯一标识，用于去重
- 支持向指定用户发送文本回复
- 记录原始事件，便于排查协议问题

### 5.2 用户与会话

- 根据微信用户 ID 自动创建用户
- 每个用户默认拥有一个主会话
- Phase 1 不提供用户主动切换会话能力
- 不同用户的历史消息、上下文和用量统计必须逻辑隔离

### 5.3 AI 人设

- 系统内置一个默认 Soul
- Soul 以文本配置形式保存
- 默认风格应偏陪伴、自然、生活化，避免工具客服感
- 不向用户暴露底层 Prompt
- 后端设计上允许后续扩展多 Soul，但 Phase 1 不做完整角色管理

### 5.4 记忆与上下文

- 保存用户消息和 AI 回复
- 每次请求拉取最近 N 轮对话
- 根据 token 上限裁剪上下文
- Phase 1 只做短期滑动窗口记忆
- 不做长期总结记忆和用户画像

### 5.5 文本生成

- 支持配置 LLM Provider、模型名、API Key、超时、最大 token
- 支持调用失败、超时、限额不足时的降级回复
- 支持记录输入 token、输出 token、耗时和错误码

### 5.6 语音识别

- 支持配置 ASR Provider、模型名、API Key 和超时
- 支持语音文件下载或读取
- 支持识别结果进入统一文本对话链路
- 支持 ASR 失败时的用户提示和日志记录

### 5.7 用量与风控

- 按用户限制短时间请求频率
- 按用户限制每日交互次数
- 按用户限制单次上下文最大 token
- 支持简单黑名单
- 避免秒级高频回复和重复发送
- 对异常失败进行退避或熔断

### 5.8 日志与观测

- 记录每条入站消息处理状态
- 记录 LLM 和 ASR 调用耗时、结果、错误
- 记录用户级每日使用量
- 记录发送成功或失败状态
- 日志中避免保存明文密钥

## 6. 非功能需求

- 稳定性：单个用户请求失败不能影响其他用户。
- 隔离性：不同用户之间不得混用上下文或历史消息。
- 可恢复性：服务重启后用户历史和用量统计不丢失。
- 可扩展性：后续可接入 RAG、更多 Soul、管理后台、付费系统。
- 成本可控：所有 LLM 与 ASR 调用必须经过限流和预算控制。
- 响应体验：文本消息常规回复目标在 5-20 秒内完成，语音消息允许更长处理时间。

## 7. 验收标准

- 至少 3 个不同微信用户可以扫码或添加账号后使用同一套服务。
- 不同用户连续对话时，上下文不会串线。
- 用户 A 提到的信息不会出现在用户 B 的回复中。
- 文本消息可以完成至少 5 轮连续对话。
- 语音消息可以被识别并得到 AI 回复。
- 达到限流阈值后，系统不会继续消耗 LLM 或 ASR 额度。
- LLM 或 ASR 故障时，用户能收到可理解的失败提示。
- 管理者可以通过日志追踪一条消息从接收到回复的完整链路。

## 8. 待确认问题

- OpenClaw 是否能稳定提供 webhook 事件和主动发送 API。
- OpenClaw 传递语音消息时提供的是媒体 URL、文件 ID，还是本地文件路径。
- 首版是否只允许白名单用户使用，还是扫码后默认开放。
- 默认每日交互次数和 token 上限是多少。
- 默认 Soul 的具体人设、语气和边界。
- 首版 LLM 与 ASR Provider 选择。
