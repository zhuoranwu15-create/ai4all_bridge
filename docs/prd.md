# 产品需求文档：AI4ALL 微信个人 AI 陪伴服务 Phase 1

更新时间：2026-06-02

## 1. 产品定位

AI4ALL 微信个人 AI 陪伴服务面向普通用户，提供一键扫码接入微信 OpenClawBot 通道的个人 AI 体验。用户不需要部署 OpenClaw、不需要配置模型或服务器，只需要完成手机号验证和微信扫码，即可在微信私聊中使用由 AI4ALL Backend 驱动的个人 AI bot。

产品第一定位是聊天陪伴，其次是轻量个人助理。核心目标是让普通人也能享受到 AI 在情感陪伴、日常陪聊、生活支持和轻量事务辅助方面带来的体验提升。

技术上复用 OpenClaw 和官方 `openclaw-weixin` 的微信连接能力，但 AI4ALL Backend 拥有产品业务状态：用户注册、扫码绑定、账号隔离、Soul、会话、记忆、提醒、主动消息、模型调用、权益用量和运营管理。

目标模型：

```text
普通用户
-> Web/H5 手机号验证
-> 扫码接入微信 OpenClawBot 通道
-> 获得一个 AI4ALL Account
-> 在微信私聊里使用个人 AI 陪伴与轻量助理服务
```

当前不采用“一个公共微信客服号服务大量外部用户”的客服号模型，也不做群聊 bot。

## 2. Phase 1 产品目标

Phase 1 的目标是完成可正式发布的内测版本，而不是只建立 Demo 级最小闭环。

- 普通用户可以通过手机号验证和微信扫码完成接入。
- 用户能在微信私聊里获得自然、温和、有持续感的陪伴式对话。
- 每个用户拥有独立 AI4ALL Account，Soul、上下文、记忆、用量和配置不串线。
- 系统具备基础运营能力，可以查看账号、绑定、会话、消息元数据/统计、用量、权益和异常。
- P0 和 P1 中定义的陪伴、提醒、主动触达、搜索、语音和垂类推送能力均完成到内测可用。
- 内测阶段以赠送贝壳为主，支持用量扣减、运营发放和拉新奖励。
- 支付和用户购买不进入 Phase 1 内测首发范围；内测阶段通过赠送、运营补发和拉新奖励支撑权益。
- Phase 1 完成后具备正式内测发布条件。

## 3. 用户与角色

### 3.1 目标用户：C 端普通用户

希望通过微信低门槛获得个人 AI 陪伴与轻量助理能力的用户。

典型需求：

- 希望有一个随时可以聊天、回应自然的 AI 陪伴对象。
- 希望 AI 在日常情绪、生活琐事、想法整理上能提供陪伴和轻量建议。
- 希望 AI 能记住近期对话和明确偏好，而不是每次都从零开始。
- 希望不用理解模型、API Key、服务器、OpenClaw 或插件配置。
- 希望在需要时获得提醒、搜索、新闻、搞笑内容等轻量辅助。

### 3.2 内部角色：运营、管理员与客服

运营、管理员和客服不是本产品的目标用户，而是保障内测发布、服务稳定、成本控制和用户支持的内部角色。

典型需求：

- 能看到用户注册、扫码绑定、通道账号和 AI4ALL Account 的关系。
- 能观察消息链路元数据、错误、用量、权益流水和模型调用状态。
- 能调整账号状态、默认风格、限流、主动触达总开关和基础配置。
- 能处理绑定异常、额度补发、误扣排查和用户反馈。
- 能确保不同用户之间的 Soul、会话、记忆和用量统计隔离。

## 4. Phase 1 范围

Phase 1 范围由三部分组成：P0、P1 和 P1.5。P0、P1 和 P1.5 都属于 Phase 1 必须完成范围。支付与用户购买已正式后置，不进入 Phase 1 内测首发范围。

### 4.1 P0：接入、对话和隔离闭环

- Web/H5 onboarding。
- 大陆手机号格式校验、阿里云验证码和短信 OTP。
- 扫码绑定微信 OpenClawBot 通道。
- 创建或复用 `platform_user`、默认 AI4ALL Account 和绑定记录。
- 微信私聊文本消息收发。
- 基于 AI4ALL Account 的 Soul、上下文、记忆、用量和配置隔离。
- 默认陪伴式 Soul：自然、温和、生活化，避免工具客服感。
- 短期上下文记忆，支持多轮连续对话。
- 基础限流、每日用量控制和失败降级回复。
- 消息元数据、账号、绑定、脱敏 raw payload 元数据、LLM 调用和错误的可观测记录。
- Admin API / 轻量后台查看账号、绑定、会话、消息统计/元数据和用量。
- 安全边界：不做医疗诊断、法律意见、金融投资建议或心理咨询替代。

### 4.2 P1：内测版完整陪伴与轻量助理能力

- 用户提醒：明确时间的一次性提醒、周期性提醒、自然语言取消/更新提醒，并在用户确认后生效调整。
- 受控主动消息：outbound ledger、quiet hours、默认日上限、分类上限、6 小时避让、幂等发送；quiet hours 默认 22:00 到次日 7:00。
- 用户级 proactive state，支持主动触达总开关；总开关只影响陪伴跟进和内容推送，不影响用户提醒。
- 陪伴跟进：从普通聊天中高置信提取 hidden commitment、后续关怀或主动搭讪候选，并在合适时间低频触达。
- 内容推送：每日新闻、搞笑内容或垂类内容推送的最小试探、生成、发送、拒绝反馈、冷却和退订模型。
- 信息搜索能力：采用 OpenClaw 风格的 `web_search` 工具；模型基于 tool schema 自然判断是否搜索，默认同步返回带来源边界的回答。
- 后台整理不支持：Phase 1 不支持用户请求后的后台整理、异步任务补发或长耗时报告生成；搜索超时、provider 失败或任务过复杂时，当前回合返回失败/不支持说明。
- 语音输入：当前依赖 `openclaw-weixin` 上游提供语音转文字正文；有上游转写文本时复用普通文本对话链路。不接入后端豆包 ASR，不承诺无转写文本时的 ASR fallback。
- 用户可理解的主动触达设置：主动触达总开关、quiet hours 和基础频率偏好；不设置分类型开关。
- 记忆机制产品化：学习 OpenClaw 的分层记忆和 Dream/Dreaming 机制，至少支持 daily notes、长期记忆沉淀、查看/重置/禁用的运营侧能力，用户侧入口可简化。

### 4.3 P1.5：权益、增长、客服与支付后置

- 贝壳：内测阶段以赠送为主，新用户注册默认赠送 1000 个贝壳，支撑运营手工发放、补偿发放、活动发放和拉新奖励。
- 产品内贝壳体系：贝壳不是链上资产，不可提现，用于记录赠送额度、运营发放额度、拉新奖励和资源消耗扣减。
- 用量扣减：默认以 `deepseek v4-flash` 为基准，1000 个基准模型 token 消耗 1 个贝壳；聊天默认按输入 token + 输出 token 加和计算；其他模型按相对基准模型价格倍率折算。
- 搜索扣减：Phase 1 暂定每次成功触发商业搜索 provider 的 `web_search` 扣减 5 个贝壳，用于覆盖约 3 分钱人民币的外部搜索成本和少量处理成本；搜索回答中的 LLM token 仍按普通聊天规则扣减。
- 价格锚点：未来如开放购买，暂定 `1 元人民币 = 100 贝壳`，该价格仅作为后续商业化锚点，Phase 1 内测不开放用户购买。
- 拉新激励：支持邀请码和带邀请码注册链接；新用户注册绑定后发送 3 条有意义信息，由后台 AI 判断，通过后暂定给邀请人发放 1000 个贝壳。
- 用户可见余额与基础流水：内测版至少能让用户或客服确认剩余贝壳数量、发放记录和消耗概况。
- 客服与运营支撑：支持处理绑定异常、额度补发、账号禁用/恢复、用户反馈和基础工单记录。
- 支付与用户购买正式后置：Phase 1 内测不实现购买、订单、支付回调、退款或自动续费，不阻塞内测发布。
- 模块归属待决：权益、拉新、客服等业务逻辑可以先在本仓库形成最小闭环，也可以拆成独立 billing/growth/support 服务；Phase 1 必须先确定 API 边界、数据归属和集成方式。支付模块后续单独立项。

### 4.4 暂不实现

- 群聊 bot。
- 一个公共服务微信号接待大量外部用户。
- 图片生成。（注：图片**理解**原列为暂不做，已在 Phase 1 收尾期提前交付，见 [Phase 1 收尾总结 §2.1](archive/phase1/phase1_closeout_summary.md)。）
- 文件处理。
- RAG 知识库。
- 复杂多 Agent 编排。
- 用户自定义角色市场。
- 用户直接编辑底层 prompt、skill 或 plugin。
- 完整公开商业化官网、复杂营销系统和多 bot 自助管理。
- 大规模客服系统。
- 小于 1 天周期的高频提醒、复杂日程管理。

## 6. 全局产品原则

- 陪伴优先：默认体验应像一个自然、温和、有持续感的个人 AI，而不是内部调试工具或客服机器人。
- 微信低门槛：普通用户不需要理解 OpenClaw、模型、服务器、插件或账号路由。
- 账号隔离：AI4ALL 业务隔离主键是 `ai4all_account_id`，不得混用不同账号的 Soul、上下文、记忆、权益或配置。
- 隐私红线：后台默认不能查看用户具体聊天记录，只能查看统计、状态、元数据和链路信息；管理员拥有最高明文权限用于必要 debug，普通后台用户如需查看明文，需要管理员审批的 2 小时临时权限；所有明文查看必须记录操作日志。
- 克制主动：用户提醒、陪伴跟进和内容推送都必须写入 outbound ledger 并幂等发送；主动触达总开关只影响陪伴跟进和内容推送，用户提醒不受该开关影响。
- 优先级避让：预判未来 6 小时内有用户提醒时，不安排陪伴跟进和内容推送；预判未来 6 小时内有陪伴跟进时，不安排内容推送。
- 同步搜索、复杂任务不后台处理：普通 Web Search 走同步工具调用；超过同步预算、provider 失败或需要深度整理时，当前回合返回失败/不支持说明，不创建后台任务。
- 记忆保守：学习 OpenClaw 的分层记忆和 Dream/Dreaming 机制，但写入必须账号隔离、可追溯、可回滚。
- 成本可控：LLM、搜索和主动消息都应受限流、预算和权益扣减控制；当前语音依赖上游转写，不单独产生后端 ASR 成本。
- 边界清晰：不替代医疗诊断、法律意见、金融投资建议或专业心理咨询。

## 7. 非功能需求

- 稳定性：单个账号失败不能影响其他账号。
- 隔离性：不同账号之间不得混用 Soul、上下文、记忆、权益或用量。
- 可恢复性：服务重启后账号、绑定、会话、消息、提醒、主动消息、用量和权益流水不丢失。
- 响应体验：普通文本回复目标在 5-20 秒内完成；普通 Web Search 在同步预算内直接回答，高耗时搜索或复杂整理当前回合返回失败/不支持说明。
- 可观测性：关键链路需要可追踪，包括注册、绑定、入站消息、LLM、工具调用、主动发送、权益扣减和错误。
- 隐私合规：正式开放前必须补充隐私政策、数据保留策略和用户告知机制。
- 内容审核：文本、图片、语音转写文本、出站回复和主动消息必须具备可追溯审核链路；普通审核异步执行，出站绝对红线需要高置信同步阻断。
- 可扩展性：Phase 1 应支持语音、搜索、内容推送、贝壳和内测运营闭环，后续可扩展支付、多渠道、多 bot 和更完整商业化后台。

## 8. 总体验收标准

P0 验收：

- 用户可以通过 Web/H5 完成手机号 OTP 验证。
- OTP 通过后，系统创建或复用 `platform_user` 和默认 AI4ALL Account。
- 用户扫码后，`binding_intents` 完成，`channel_bindings` 写入通道账号。
- 扫码后的真实微信私聊消息能路由到预创建 `aid_...`。
- 至少 2 个不同用户/账号可以同时使用，且上下文不串线。
- 同一账号可以完成至少 5 轮连续文本对话。
- 默认回复风格符合陪伴式定位，不像内部调试工具或客服机器人。
- 达到限流阈值后，系统不继续消耗 LLM 额度。
- LLM 故障时，用户能收到可理解的失败提示。
- 管理者能通过 Admin API 或后台基于元数据追踪一条消息从接收到回复的链路。

P1 验收：

- 明确时间的一次性提醒可以创建、到期、发送并回写状态。
- 周期性提醒可以创建、到期发送，并正确计算下一次触发时间；系统不创建小于 1 天周期的高频提醒。
- 自然语言取消和更新提醒需要先返回拟调整结果，用户确认后才生效。
- 无法合理推断时间的模糊提醒不会误创建任务，会要求用户补充具体日期和时间。
- 用户提醒不受主动触达总开关和默认每日主动消息上限影响。
- 用户提醒命中 quiet hours 时，仍严格按用户设定时间发送。
- 陪伴跟进和内容推送遵守主动触达总开关、quiet hours、默认日上限、分类上限和 outbound ledger。
- 陪伴跟进和内容推送默认每日上限分别为 1 条。
- 各垂类内容默认试探频率为每天最多 1 次；受内容推送类型总日上限约束，同一天最多实际发送 1 条内容推送。
- 主动消息调度满足 6 小时避让规则：用户提醒压制陪伴跟进和内容推送，陪伴跟进压制内容推送。
- 用户提醒、陪伴跟进、内容推送三类消息在记录、频控和设置上可区分。
- 陪伴跟进不会在用户未开启、没有高置信候选或超过频率限制时发送。
- 每日新闻、搞笑内容或其他内容推送支持低频试探、限频、明确拒绝识别、冷却和退订。
- Web Search 能通过 LLM tool use 自然触发，普通搜索在当前 turn 同步返回带来源边界的回答。
- 搜索超时、provider 失败、结果不足或复杂后台整理请求会在当前回合给出可理解说明，不创建后台任务，不承诺补发。
- 搜索工具调用能记录 provider、状态、耗时、失败原因和成本明细；成功触发商业搜索 provider 暂定扣减 5 个贝壳。
- 微信语音输入在 `openclaw-weixin` 提供上游转写文本时，可以进入统一文本对话链路；当前不接入后端豆包 ASR。
- 文本、图片、语音转写文本、出站回复和主动消息能进入审核链路；默认抽检比例为入站 15%、出站 30%、主动消息 100%，且所有审核记录按账号隔离。
- 记忆机制至少具备 daily notes、长期记忆沉淀和 Dream/Dreaming 风格蒸馏链路，且不同账号记忆不串线。

P1.5 验收：

- 新用户注册成功后可以获得 1000 个贝壳，贝壳能生效到账号。
- LLM / 搜索等消耗能生成贝壳扣减流水；默认聊天按 `1000 deepseek v4-flash token = 1 贝壳` 扣减；成功触发商业搜索 provider 暂定扣减 5 个贝壳。
- 主动触达首条消息不扣用户贝壳；用户回复后产生的 AI 回复或任务执行，从该后续链路开始按普通聊天或任务规则扣减。
- 邀请新用户完成注册/绑定并发送 3 条有意义信息后，可以按规则给邀请人发放拉新奖励。
- 管理者可以补发贝壳、查看邀请关系、排查误扣并记录基础客服处理。
- 支付/购买正式后置，不作为 Phase 1 内测验收项；后续如开放购买，价格锚点暂定 `1 元人民币 = 100 贝壳`。
- Phase 1 完成后具备正式内测发布条件。

## 9. 全局待确认问题

- 对外产品名称、bot 名称和默认称呼。
- 默认 Soul 的具体人设、语气、幽默感和边界。
- Onboarding 页面文案：如何向普通用户解释“扫码接入”而不暴露过多技术细节。
- 重复绑定、解绑、换微信号、找回账号的产品策略。
- 免费/内测阶段的默认每日交互次数、主动消息次数和 token 上限。
- 主动消息的用户授权方式和退订入口。
- 搜索引用格式和引用边界。
- 语音输入的优先级、媒体保留策略和失败体验。
- 内容推送的内容来源、内容审核策略和垂类内容白名单。

- 支付后续立项时的 Provider、套餐结构、退款策略和支付合规边界。
- 商业化、拉新和客服逻辑是否放在本仓库，还是拆成独立 billing/growth/support 服务。
- 正式开放前的隐私政策、数据保留和用户删除数据流程。
