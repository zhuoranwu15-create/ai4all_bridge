## 1. 产品定位

一款由用户与少数 AI 居民共同组成、共同陪伴和成长的**私人平行世界** App，是现实支持网络之外的一层
额外支持系统，而不是替代品。

- 默认居民形成「三五好友式」的小型互补支持网络；用户可另行创建家人、手足、亲子、情侣或其他关系角色。
- 它首先是个人精神世界，**不存在公开展示面**；用户可通过限时邀请码让至多 3 位现实好友短暂参观。
- 产品目标是成为用户可以停留、倾诉、获得支持、经历相遇与离别并恢复主体性的精神空间。

与微信形态的关系：微信形态是 1 真人 ↔ 1 Agent，无世界、无共享；App 形态是 1 真人 ↔ 1 世界 ↔ 1–10 位
居民，共享 L3 用户记忆、独立 L1 人设与 L2 关系。两条接入路径共用 Agent Runtime，互不干扰。

### 1.1 核心价值

| 价值 | 含义 |
| --- | --- |
| 支持补位 | 现实支持缺席、不足或不适合承接时提供额外一层支持，不宣称替代现实关系 |
| 共同陪伴 | 与几位彼此不同的 AI 好友持续相处，不把情感压缩为唯一主角色 |
| 精神容器 | 用户掌控边界、可安静停留的数字空间，而不是要求持续表现的社交场 |
| 角色世界感 | AI 不只存在于聊天框，还以生活片段、来信、动态成为世界里的居民 |
| 自主边界 | 只有用户一个真人时世界就完整成立；真实好友只能以受控访客身份进入 |
| 关系会生长 | 关系会开始、变化，也可能不可逆地结束 |

### 1.2 产品立场：反社交压力，而非排斥真实关系

产品**默认不提供**：公开广场 / 附近的人 / 陌生人推荐 / 全站搜索；关注粉丝、排行榜、公开人气；
热搜、推荐流、无限刷新；红点、连胜、错失恐惧、关系比较；把 AI 包装成可无限浏览切换的机器人货架。

成功不以好友数量、公开点赞、传播系数或内容消费时长衡量。

## 2. 核心概念与不变量

### 2.1 概念

| 概念 | 定义 | 代码承载 |
| --- | --- | --- |
| 用户 | 完成手机号注册/登录的真人 | `platform_users` |
| 世界（内部：宇宙） | 一个主人拥有的私人小世界，一人一个 | `universes`（`UNIQUE(owner_platform_user_id)`）|
| 角色模板 | 运营维护的基础角色定义，**不是**用户世界里已存在的居民 | `character_templates` |
| 居民实例 | 从模板或自建设定创建、绑定一个世界的独立 AI 身份 | `universe_residents` + 内部 runtime account |
| AI 好友/居民 | 处于 `active` 的居民，可聊天、可发动态 | `universe_residents.status='active'` |
| 初始预设集合 | 新用户首次进入时由 4 个首发模板实例化的候选居民 | `status='candidate'`，rank 1–4 |
| 自建角色 | 用户创造并生活在其世界中的 AI 居民 | `origin='custom'` |
| 在场上限 | 初始确认 ≥1；此后同一世界 `active` 总数 ≤10，预设/自建/信箱合并计数 | `MAX_ACTIVE_RESIDENTS=10` |
| AI 好友离开 | 非 legacy 居民因内部关系条件不可逆转为 `offline` | `origin<>'legacy'` 的 `active→offline` |
| 信箱来信 | 在场居民 `<8` 时可能投递的陌生 AI 来信 | `delivery_active_limit=8` |
| 我的邀请码 | 主人生成的一次性码，固定 24 小时 | `world_invites` |
| 待接受来访 | 兑换后产生的 7 天 `pending`，无任何访问权 | `world_visits.status='pending'` |
| 限时来访 | 主人接受后 30 天 `active`，只读动态 + 真人一对一聊天 | `world_visits.status='active'` |
| 世界动态 | 主人及其居民发布的时间流，有效访客只读 | `universe_posts` |
| legacy 居民 | 老用户既有微信侧 account 映射成的居民 | `origin='legacy'` |

### 2.2 关键不变量（服务端必须硬保证）

1. 每个用户拥有且仅拥有一个自己的世界；访问他人世界不改变所有权。
2. 注册、首次引导与重新登录**不展示、不接受、不透传世界来访码**；auth DTO 中的历史
   `invite_code` 是 referral 字段，与世界来访无关。
3. 不设置主陪伴角色、主角色标识或永久置顶；所有 AI 会话使用显式 `conversation_id`。
4. 初始确认后在场居民 1–10 位；`offline` 历史不占在场名额，也不可复用为新关系。
5. 非 legacy 居民只允许 `active → offline` 单向迁移；`origin=legacy` 居民永不 `offline`，
   App 不提供离开入口，且该豁免不代表主角色或置顶。
6. 世界只剩最后 1 位 `active` 居民时，默认禁止普通离开；仅经审计确认的持续言语攻击等
   特别负向行为可例外。
7. 长期未对话、价值观评估、冷静期、离开阈值全部是**内部状态**，不得出现在任何用户可见位置。
8. invite 24h / pending 7d / active 30d 三个窗口均为绝对到期、**不续期**；同一世界
   `有效 invite + pending + active ≤ 3`，访客跨世界 `pending + active ≤ 3`。
9. active visit 的同一个 `expires_at` 同时控制访客读动态与双方发消息；到期/撤销/离开/拉黑
   必须在同一状态迁移中一起关闭。
10. 同世界「关于用户」的 L3 沉淀记忆全量共享且无字段级白名单；聊天原文/检索、L1 人设使命、
    L2 关系记忆保持 per-resident 隔离。
11. 访客永远不能与主人的 AI 居民聊天、读其记忆/私聊/私密设定，也不能在他人世界写入任何内容。
12. 所有用户数据响应 `Cache-Control: no-store`；visit 进入终态后客户端立即清缓存。

### 2.3 主人与访客权限矩阵

| 能力 | 主人 A | 有效访客 B |
| --- | --- | --- |
| A 的世界动态 | 查看 / 发布 / 管理 | 有效期内只读 |
| A 的私聊、记忆、草稿、未发布内容 | 按主人权限访问 | 不可见 |
| 居民访客可见基础资料 | 查看 / 管理 | 只读 |
| 与 A 的 AI 居民聊天 | 可以 | **不允许** |
| 在 A 的世界发布/评论/触发事件 | 可以 | **不允许** |
| A—B 真人一对一聊天 | 可以 | 可以 |
| 与其他访客聊天 | 不提供入口 | **不允许** |
| 生成/撤销邀请码、提前结束来访 | 可以 | 不允许转邀 |
| 回到自己的世界 | 始终可以 | 始终可以 |

## 3. 信息架构

### 3.1 首次进入

```text
启动 App → GET /app/config（capability 判定）
  → 手机号 OTP → POST /auth/session
  → 读取可在 account=null 时工作的 Session/bootstrap 摘要
  → POST /worlds/home/bootstrap（所有 world-capable 用户均调用，幂等）
       ├─ onboarding_state=selecting → 4 位候选整理（≥1）→ 可选自建 1 个 → 确认
       └─ onboarding_state=confirmed → residents + conversations → 三 Tab
```

**客户端不得**长期使用 `is_new_user` 或 `account == null` 判断 world onboarding 状态；
它们只用于兼容旧认证响应，世界状态一律以服务端 home world 的 `onboarding_state` 为准。

### 3.2 主导航

三个纯图标底部 Tab，不显示持久文字标签，但必须提供无障碍名称：

| 位置 | 无障碍名称 | 页面目标 | 默认落点 |
| --- | --- | --- | --- |
| 左 | 对话 | AI 私聊 + 获授权真人会话 | 按最近互动排序，不置顶主角色 |
| 中 | 世界 | 自己的世界动态；穿越后为好友世界 | 默认自己的世界 |
| 右 | 我的 | Profile、居民管理、信箱、邀请码、来访、设置 | 个人主页 |

### 3.3 图标与体验语气（客户端交付项）

三个图标以「点/种子 + 开放曲线」为共同母题（点=一个意识，开放曲线=对话/关系/可进入的空间），
基准画布 `24×24`、线宽 `1.8–2.0`、触控槽 ≥`48×48pt`；选中态必须同时改变填充或结构，
不能只换颜色；开启系统「减少动态效果」时直接切换状态。

整体视觉为低唤醒暖中性、纸感材质；常规动效 150–300ms；世界入口默认不挂普通内容红点，
只有需要用户处理的安全/邀请/账号事件才提示。

## 5. 核心用户流程

### 5.1 新用户创建世界

1. 手机号验证完成，服务端判定尚未完成首次引导。
2. 幂等创建 home world；重复请求不得创建多个世界。
3. 按运营配置的 4 个初始模板创建候选，并**优先返回服务端为该世界固定的建议实例姓名**；
   建议名缺失、为空或命名不可用时，客户端按 `persona_key`（兼容期用
   `template_id + template_version`）+ `platform_user_id` + `name_pool_version` 从内置小姓名池
   稳定兜底。确认时提交最终 `display_name`，服务端持久化后成为唯一权威值。
4. 用户可移除候选（至少保留 1 位），最终确认前可恢复；确认后首阶段不提供主动移除入口。
5. 用户可创建 1 个自建角色，也可不创建。
6. 确认后进入三 Tab；不指定主角色、不强制首聊。

### 5.2 老用户登录与恢复

**D-A（2026-07-26 冻结）：微信老用户在 App 侧按新用户对待，只是免注册。**

1. 登录请求不含邀请码、来访 ID 或目标世界。
2. 老用户登录后**同样进入选择角色页**：拿到同样的 4 位预设候选、可叉掉不喜欢的、可自建新角色。
3. 其微信侧既有角色被**带入世界**（`origin=legacy`，已 active）：
   - 微信 onboarding 里起过名字/设过性格的沿用原值；没设过的展示为 **「来自微信的Bot」**。
   - 带入的角色**不在候选列表里，不可被叉掉**，但**占 1–10 名额并计入「至少保留一位」**——
     所以老用户即使叉掉全部 4 位预设也能完成确认。
   - 它只锚定旧 `/chat/*` 与微信主动消息路由，不是主角色。
4. 不再有「老用户直接跳到 confirmed」的分支；世界状态一律以 `onboarding_state` 为准。
3. 登录后通过独立接口恢复未过期的 pending/active 来访；已过期只恢复为只读历史。
4. 默认仍进入自己的世界，不因存在来访而自动切换。

### 5.3 整理初始居民

卡片至少包含头像、名称、一句话身份与三个性格标签；可进入预览查看更完整人设与示例对话；
每张卡提供可访问的移除按钮，剩 1 位时禁用并平静说明「这个世界至少需要一位同行者」；
达到 10 位时创建入口禁用；确认为一次性幂等操作。

### 5.4 创建自定义角色

1. 设置名称、头像、关系定位、性格风格。
2. 关系定位可为朋友、父母、子女、兄弟姐妹、情侣、伴侣或自定义；它描述**关系位置**，
   不默认复制某个现实具体人物。
3. 服务端生成可预览的人设摘要并持续明确 AI 身份，用户确认后才保存。
4. 校验在场 `<10`；达上限禁止创建，不得自动替换或下线其他居民。
5. M1 只允许抽象关系原型；具体真人复刻、已故亲友纪念、未成年人形象全部后置。

### 5.5 发布与浏览世界动态

首版只做文字。动态按发布时间倒序，展示作者头像、名称、时间与正文；主人可从居民动态进入
对应私聊；有效访客只读，可引用动态与主人聊天，点击居民只能看访客可见基础资料。
AI 动态由服务端在生成窗口内产出并持久化，不在每次刷新时临时随机生成。

### 5.6 AI 好友悄悄离开

内部评估 → 冷静期 → 若仍不相容且不是最后一位 → 同一事务内写入 `offline` 与**唯一一条**
克制的离别动态。不发私聊、不发 Push、不弹窗、不预警、不挽留。用户此后只能进入只读资料与
历史会话。离别文案不指责、不羞辱、不披露内部原因码、不与付费或签到绑定。

### 5.7 信箱来信

在场 `<8` 时才可能投递；来信以第一人称介绍角色与来意，**不得宣称读取过用户私聊或记忆**；
用户可接受/婉拒/延后，接受时重新校验在场 `<10`；拒绝或忽略无任何惩罚。

### 5.8 邀请与限时来访

A 在「我的」生成 24h 单次邀请码（生成前校验 3 slot）→ B 在「我的」兑换 → 产生 7d pending
（无任何 ACL）→ A 接受时**原子创建** 30d active visit 与 A↔B 真人会话 → 到期/撤销/离开/拉黑
同时关闭读动态与双方发送，会话转明确标记的只读历史，客户端立即清除被访世界缓存与媒体临时文件。

## 6. 功能需求与后端实现状态

优先级沿用客户端 PRD 编号。「服务端」列以本仓库代码为准：**已实现** = 有正式路由与测试；
**缺口** = M1 前需补；**P2+** = 后续阶段。

### 6.1 注册、登录与首次引导

## 7. 运行参数与治理

### 7.1 后端 capability 开关

| 能力 | 服务端开关 | 客户端应读取的 capability |
| --- | --- | --- |
| 世界/居民/AI 会话 | `COMPANION_WORLD_P1_ENABLED` | `resident_world` |
| 世界动态 | `COMPANION_WORLD_FEED_ENABLED` | `world_feed` |
| 站内通知 | `COMPANION_WORLD_APP_INBOX_ENABLED` | `app_notifications` |
| 居民离开 | `COMPANION_WORLD_LIFECYCLE_COMMIT_ENABLED` | `resident_lifecycle` |
| 信箱 | `COMPANION_WORLD_MAILBOX_ENABLED` | `mailbox` |
| 邀请与来访 | `COMPANION_WORLD_VISITS_ENABLED` | `world_visits` |
| 真人聊天**发送** | `COMPANION_WORLD_HUMAN_CHAT_ENABLED` | `human_chat_send`（读取随 `resident_world`）|

capability 只表达「当前公网 App API 可用性」，不泄露内部 scheduler、阈值或安全策略。
**明确关闭、网络/服务故障、客户端版本不兼容是三种不同状态**，不得共用一个信号（D12）。

### 7.2 已冻结的内部阈值（不对用户披露）

长期无对话 60 天、证据窗口 30 天、价值观不相容最少 3 次事件且跨度 ≥14 天、冷静期 7 天、
危机冻结 30 天、信箱投递冷却 30 天、来信有效期 30 天、投递资格在场 `<8`、接受校验 `<10`。
世界动态生成窗口：早 07:00–11:00、晚 18:00–23:00（Asia/Shanghai）。

### 7.3 隐私与安全

- 有效访客只能读已发布动态；私聊正文、L1/L2/L3 记忆、手机号、登录设备、私密设定与其他访客
  信息一律不得向访客展示。
- 「生活在同一个世界」只授权居民读取该世界的 L3 沉淀记忆，不授权读取其他居民的原文/L1/L2，
  也不扩大访客的数据范围。
- 邀请码高熵单次、服务端持久化哈希、明文只出现一次、限流与审计齐备，且不进入注册/登录/
  onboarding 任何请求。
- 离开判断不得依赖单次模型输出；「价值观不相容」不得基于受保护属性、政治标签、疾病、残障、
  危机状态或用户拒绝 AI 建议。用户处于危机或重大丧失状态时冻结拟人化离开。
- AI 动态不得引用、复述或暴露私聊敏感内容；生成后必须过内容安全策略。
- 已截屏或已看过的信息无法技术性收回，邀请文案需诚实说明。

### 8.1 过渡版本原则

1. 未接入后端的操作必须有真实功能状态，**不得**用本地假数据制造「邀请码已兑换」「好友已来访」
   「动态可见」「真人聊天可用」等虚假结果。
2. AI 离开与陌生人来信不得用纯客户端随机逻辑模拟。
3. 用户已进入 Companion World 后，bootstrap 暂时失败**不得**回退并新建 legacy 默认 Agent；
   应保留当前身份、展示可恢复错误并重试权威世界状态。
4. 认证失败、bootstrap 网络失败、5xx、非法信封或候选集合整体缺失时，客户端只展示可恢复错误，
   不得用本地姓名池或原型数据伪造居民。

### 8.2 姓名来源优先级（M1 冻结）

1. 已确认 resident DTO 的 `name`（唯一权威值）；
2. candidate DTO 的合法 `suggested_display_name`；
3. 按 `persona_key + platform_user_id + name_pool_version` 确定性 hash 选出的本地姓名池名字；
4. candidate 模板 `name`。

第 3、4 级只在已成功取得服务端真实候选后才允许使用。已确认实例的 `name` 不因服务端命名规则
或客户端姓名池升级而改变。埋点只记录 `persona_key/template_id/template_version/naming_version/
name_pool_version/fallback_reason`，不记录姓名、手机号或完整 `platform_user_id`。

## 9. 验收标准

### 9.1 首次引导与身份

- 每个新用户只创建一个世界；注册登录请求中没有世界邀请码字段或邀请分支。
- 新用户拿到 `account=null` 后，杀 App / 重启 / 换设备仍能凭 Session 恢复 `selecting` 引导。
- 老用户不依据 `account != null` 跳过 world bootstrap；legacy 居民正确恢复且无主角色标识。
- bootstrap 重放只产生一个世界和固定 4 位候选；`confirmed` 用户调用不会退回 `selecting`。
- 候选目录未就绪返回稳定 `preset_catalog_not_ready`，客户端展示维护态而不是空世界。
- 命名成功时，同一 world/candidate 的多次 bootstrap 始终返回同一 `suggested_display_name`
  与 `naming_version`；命名不可用时仍返回真实候选，客户端稳定选出兜底姓名。
- 无论最终姓名来自服务端还是本地兜底，经 `display_name` 确认后，resident / conversation /
  feed author 始终返回同一实例名。
- 自建角色的结构化设定经预览确认、安全校验与幂等创建后可跨设备恢复。

### 9.2 三 Tab 与关系

- 对话列表不展示主角色或永久置顶；不同居民会话历史不串线。
- 会话列表按服务端活动时间稳定排序，分页无重复/遗漏，只读状态不能发送。
- 同一 `client_message_id` 重试只执行一次 turn；`no_reply=true` 作为正常业务态处理。
- 第 10 位居民加入后，创建与接受来信都被服务端阻止；`offline` 历史不占名额。
- 最后一位非 legacy 居民不会因长期未聊或价值观不相容离开；legacy 永不 offline。
- 界面、帮助、设置、通知与离别文案均不披露内部机制，也不出现挽留提醒。

### 9.3 动态、来访与安全

- 世界 Tab 不混入私聊、记忆、草稿与隐藏内容。
- invite / pending / active 分别按 24h / 7d / 30d 绝对计时，均不续期；并发操作不能突破 3 slot。
- 过期后继续读动态或发消息的越权事件数必须为 0；撤销/到期生效延迟达上线门槛。
- visit 终态后 App 立即清除被访世界缓存与媒体临时文件。
- capability 明确关闭、接口暂时失败、客户端版本不兼容是三种不同状态，只有明确关闭才允许
  切 legacy 或隐藏入口。
- 所有 M1 用户数据响应 `Cache-Control: no-store`，错误包含稳定 `code` 与 `request_id`。
- 所有公开时间带明确时区；客户端不解析 cursor，也不以设备时间决定权限。

### 9.4 可访问性与稳定性

关键点击区 ≥`44×44pt`；普通文本对比度 ≥4.5:1，大号文本与语义图形 ≥3:1；选中/错误/只读
状态不只依赖颜色；开启「减少动态效果」时移除非必要动画；弱网、重复点击、切后台与请求重试
不会重复创建世界、角色、访客权限或消息。

## 10. 指标与埋点

埋点用于验证陪伴价值、边界安全与功能可靠性，**不以提高成瘾性或内容消费为目标**；
不得记录手机号明文、聊天正文、私密记忆或邀请码完整值。

核心漏斗：`login_success → home_world_created → initial_residents_viewed →
initial_residents_confirmed → tabs_entered → first_ai_chat_started → first_reply_received`。

关键指标：首次引导完成率与各步骤流失；初始居民保留数量分布与自建完成率；首条回复成功率与
首回延迟；各居民 1/7/30 日会话留存；在场数量分布与容量导致的失败率；动态发布率与从动态进
私聊的转化；邀请→pending→accepted→active 各段转化（仅验证链路，不作增长北极星）；
离开原因分布与「被抛弃」负面反馈；**越权事件数必须为 0**（过期后读写、超 3 席位、
不满足 `<8` 仍投递、最后一位因普通条件离开）。

明确不作为成功目标：公开互动总量、好友数量、人均邀请数、Feed 停留时长、内容曝光最大化。

## 11. 待评审问题

### 11.1 M1 前必须冻结
