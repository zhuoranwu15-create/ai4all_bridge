# 产品专题 PRD：用户标签与元属性建设

更新时间：2026-06-18

## 1. 背景

AI4ALL 微信 Bot 是个人 AI 陪伴产品，不是客服机器人。用户标签与元属性的目标不是给用户贴粗暴标签，而是在账号隔离、隐私最小化和安全可控的前提下，把少量稳定、可解释的账号级信号结构化。

当前版本只保留三类核心属性：

- 活跃与消息强度：用截止昨日的累计用户入站消息数计算粗粒度强度。
- 陪伴类型标签：识别用户主要使用 AI 陪伴的场景和需求。
- 安全与风险属性：记录最近 30 天安全风险触发次数。

生命周期属性、回复风格与偏好、话题兴趣、主动触达反馈、权益增长与反作弊、记忆与上下文健康属性暂不进入本期用户元属性体系。建表时可保留用户注册日期，作为基础事实字段和分析辅助，不单独建设生命周期标签。

本文档定义产品口径和字段初版。具体表结构、ETL、每日更新链路和 Admin UI 展示方式后续进入技术设计。

## 2. 目标

- 建立账号级用户元属性体系，支撑更稳定的陪伴体验、基础运营观测和安全风控。
- 区分可观测事实、推断标签和运营/风控状态，避免把不确定推断当作事实。
- 用元数据优先满足运营和风控需求，默认不读取或展示聊天正文。
- 所有属性按 AI4ALL Account 隔离，任何聚合、查询、写入和使用都必须带 `account_id`。
- 为后续 nearline analytics、Admin 账号视图和 prompt/context 动态装载提供统一口径。

## 3. 非目标

- 不做广告投放画像，不对外出售或共享用户画像。
- 不推断或沉淀不必要的敏感身份属性，例如真实姓名、身份证、精确住址、政治立场、宗教信仰、健康诊断、未成年人身份等。
- 不把用户一次性的情绪表达、玩笑或角色扮演请求直接固化为长期标签。
- 不让标签绕过 Safety、用户明确禁忌、主动触达设置和账号隔离规则。
- 不把标签体系替代 `USER.md`、`SOUL.md`、`MEMORY.md`。标签是结构化运营与调度信号，Context Files 是对话上下文和长期设定。

## 4. 设计原则

### 4.1 账号隔离

所有字段以 AI4ALL Account 为最小粒度。一个微信账号、一个 Soul、一个对话状态和一套记忆互相隔离。不得因为手机号、设备、邀请关系或后台查询，把不同账号的标签合并使用。

### 4.2 事实与推断分离

用户元属性分为三类：

| 类型 | 示例 | 处理原则 |
| --- | --- | --- |
| 可观测事实 | 注册日期、累计入站消息数 | 可直接计算，可审计 |
| 推断标签 | 陪伴类型 | 必须有置信度、更新时间和过期策略 |
| 运营/风控状态 | 最近 30 天安全风险触发次数 | 必须可审计，人工操作需记录原因 |

注册日期是基础事实字段，不延伸为 `registered_days`、`registered_bucket`、`lifecycle_stage` 等生命周期标签。

### 4.3 隐私最小化

标签生产和展示默认只使用元数据、计数、状态、脱敏摘要和模型输出的结构化结果。后台页面默认不得展示用户聊天正文。需要查看正文时，复用现有 Admin / Reviewer 明文权限和审计规则。

### 4.4 可解释与可回滚

关键标签至少保存 `source`、`confidence`、`last_evaluated_at`、`expires_at` 或等价信息。人工覆盖、用户纠正、风控处置和自动重算都应可追溯、可回滚。

### 4.5 简单稳定优先

本期数值属性优先采用可直接计算的粗粒度指标。暂不引入多窗口活跃、复杂分层、加权风险分、topic 冷却、权益反作弊等派生逻辑。

### 4.6 天级更新

用户标签数据是天级更新，不承诺实时生效。用户入站消息、safety event 等原始事实仍按业务链路实时写入事实表；`account_user_meta` 等派生标签表每日批处理生成或覆盖一次，统一反映截止上一自然日的数据。

## 5. 使用场景

| 场景 | 使用方式 | 边界 |
| --- | --- | --- |
| 陪伴体验 | 使用陪伴类型标签辅助判断回复重心，例如情绪承接、实用任务、学习成长 | 不突破 Safety，不主动升级亲密关系 |
| 风控审核 | 使用最近 30 天安全风险触发次数辅助抽检和排查 | 原始次数不自动等同封禁或限制 |
| 运营后台 | 展示账号注册日期、消息强度、安全风险次数、陪伴类型 | 默认不展示聊天正文 |
| 数据分析 | 观察累计消息深度、陪伴类型分布、安全风险分布 | 聚合报告需排除 debug 账号 |

## 6. 属性分层初版

### 6.1 基础事实：注册日期

生命周期属性本期去掉。建表时仅保留用户注册日期，作为基础事实字段。

| 字段 | 类型 | 口径 | 用途 |
| --- | --- | --- | --- |
| `registered_at` | datetime | 账号创建时间，优先复用 `accounts.created_at` | 账号排查、基础分析、后续 cohort 计算来源 |

说明：

- `registered_at` 不作为用户标签进入 prompt。
- 本期不生成 `registered_days`、`registered_bucket`、`first_active_at`、`days_since_last_inbound`、`lifecycle_stage`、`onboarding_state` 等生命周期属性。

### 6.2 活跃与消息强度

活跃与消息强度只保留一个粗粒度派生字段：对截止昨日的累计用户入站消息数取 log 后取整，每日更新。

| 字段 | 类型 | 口径 | 用途 |
| --- | --- | --- | --- |
| `message_intensity_level` | integer | `floor(ln(1 + inbound_message_count_until_yesterday))` | 表征截止昨日的累计消息数量强度 |

口径说明：

- `inbound_message_count_until_yesterday` 指该账号从注册至昨日 23:59:59 的用户入站消息累计条数。
- 默认使用自然对数 `ln(1 + x)`，避免 0 消息账号计算异常。
- 取整方式使用向下取整 `floor`；0 消息账号结果为 0。
- 每日离线或 nearline 更新一次，字段含义始终是“截止昨日”的累计强度，不表达今日实时活跃。
- 默认以用户入站消息衡量，不把系统主动消息或 AI 出站回复计入。
- 本期不建设近 7 / 30 天消息数、活跃天数、session 深度、有意义消息数等复杂指标。

### 6.3 陪伴类型标签

陪伴类型是推断标签，不是用户身份。一个账号可以有多个类型，需保存主类型、次类型、置信度和更新时间。该标签同样按天级更新，不因单条实时消息立即改写。

建议结构：

```text
companion_primary_type: enum
companion_secondary_types: list[enum]
companion_type_confidence: 0.0-1.0
companion_type_last_evaluated_at: datetime
```

初版类型：

| 类型 | 说明 | 典型信号 | 产品使用 | 约束 |
| --- | --- | --- | --- | --- |
| `emotional_support` 情绪陪伴 | 倾诉、安慰、被理解 | 频繁表达压力、委屈、孤独、关系烦恼 | 更重承接，少说教 | 涉及自伤时切 Safety |
| `life_reflection` 思考人生 | 价值观、选择、意义、长期规划 | 讨论人生方向、关系边界、目标取舍 | 帮用户梳理问题、给开放式追问 | 不扮演心理咨询师 |
| `romance_roleplay` 恋爱/暧昧扮演 | 用户希望更亲密或角色化互动 | 明确要求恋爱感、暧昧称呼、虚拟伴侣 | 语气更亲近但克制 | 未成年风险、性内容、依赖诱导禁用 |
| `practical_assistant` 实用主义 | 任务、效率、信息整理 | 频繁请求计划、总结、提醒、搜索 | 直接、结构化、可执行 | 不承诺未接入能力 |
| `learning_growth` 学习成长 | 学知识、练技能、求解释 | 课程、语言、代码、考试、读书 | 分步骤讲解、练习反馈 | 不伪造权威来源 |
| `work_career` 工作事业 | 工作、创业、产品、管理 | 需求分析、方案、职场沟通 | 更专业、少闲聊 | 不替代法律/财务建议 |
| `parenting_family` 亲子/家庭议题 | 育儿、家庭沟通、亲子关系 | 询问孩子教育、父母伴侣沟通 | 温和、现实可行 | 不面向未成年人做不当亲密陪伴 |
| `daily_chat` 日常闲聊 | 陪用户打发时间、轻松聊天 | 日常分享、吐槽、表情、碎碎念 | 自然轻量、有连续性 | 不高频主动打扰 |
| `content_explorer` 内容探索 | 新闻、话题、兴趣内容 | 反复关注 AI、游戏、运动、财经等内容 | 对话中做相关信息延展 | 无明确兴趣不主动推 |
| `creative_expression` 创作表达 | 写作、脑暴、角色设定、文案 | 让 AI 写段子、故事、设定、标题 | 更有创意和备选项 | 不生成违规内容 |

判定规则建议：

- 不因单条消息直接切主类型，至少需要多轮稳定信号或用户明确表达。
- 类型可多选，但 prompt 注入时只使用最相关的 1-2 个，避免过度画像。
- `romance_roleplay` 只能来自用户明确偏好或长期稳定互动，不允许系统主动诱导；触发未成年人、安全或依赖风险时降级为普通情绪陪伴或拒绝。
- `parenting_family` 指亲子/家庭议题，不等于把孩子作为直接陪伴对象。

### 6.4 安全与风险属性

安全属性用于风控、审核和保护用户，不用于增强亲密化或营销。本期只保存最近 30 天安全风险触发原始次数。

| 字段 | 类型 | 口径 | 用途 |
| --- | --- | --- | --- |
| `safety_risk_trigger_count_30d` | integer | 最近 30 天账号触发安全风险的原始次数 | 风控排查、审核优先级参考 |

口径说明：

- 统计窗口为最近 30 天滚动窗口。
- 只保存原始次数，不计算加权分、不拆分类别、不保存最高风险等级。
- `pass` 或无风险结果不计入；被安全模块判定为 `review`、`block`、`escalate` 或等价风险状态的事件计入。
- 同一条消息命中多个风险类别时，默认计为 1 次风险触发，避免类别数量放大次数。
- 入站云审核命中、出站本地阻断、主动消息阻断、记忆候选风险标记如已进入统一 safety event 流，可统一归一到账号级风险计数。
- 高风险内容不得写入长期记忆、主动消息候选或内容邀请素材。
- 涉及自伤、未成年人、隐私、医疗法律金融越界时，Safety 高于所有陪伴类型和用户偏好。

## 7. 字段存储建议

后续技术设计可考虑三层存储：

| 层 | 内容 | 更新方式 | 用途 |
| --- | --- | --- | --- |
| 事实层 | `accounts.created_at`、用户入站消息、safety events 等原始事实 | 业务写入 | 可审计来源 |
| 派生属性层 | 账号级当前属性快照，例如 `account_user_meta` | 每日批处理生成或覆盖 | Admin、策略、prompt |
| 历史快照层 | 每日属性快照，例如 `account_user_meta_daily` | nearline 每日生成 | 分析、趋势、回溯 |

派生属性建议字段：

```text
account_id
registered_at
message_intensity_level
companion_primary_type
companion_secondary_types
companion_type_confidence
companion_type_last_evaluated_at
safety_risk_trigger_count_30d
last_evaluated_at
created_at
updated_at
```

说明：

- `registered_at` 可以直接来自 `accounts.created_at`，也可以在快照表中冗余保存，便于 Admin 查询和离线分析。
- 派生属性表按天级更新，默认反映截止上一自然日的标签状态；当天新事件只进入事实层，不要求同步刷新标签表。
- 如果采用 key-value 模型，仍需保证所有 key 都以 `account_id` 为主过滤条件。
- 如果采用宽表快照，应避免提前加入本期已裁掉的属性列，降低维护成本和解释成本。

## 8. Prompt 与策略使用边界

- 普通聊天 prompt 不应全量注入所有标签，只注入与当前场景相关、置信度足够、不过期的少量陪伴类型信息。
- `message_intensity_level` 是运营和策略信号，默认不直接进入用户可见回复。
- 安全属性只用于安全分流、降级和审核，不用于让 AI 更亲密、更黏人或更会营销。
- 风险次数、注册日期等后台属性默认不进入用户可见回复。
- 用户明确纠正偏好时，后续回复应以用户明确偏好为准，并触发相关推断标签降权或过期。

## 9. 建设优先级

### Phase 1：可计算元属性 + 陪伴类型标签

本期一次上线可计算元属性和陪伴类型初版：

- 注册日期：`registered_at`，复用或冗余 `accounts.created_at`。
- 消息强度：`message_intensity_level`，每日按截止昨日累计入站消息数重算。
- 安全风险：`safety_risk_trigger_count_30d`，最近 30 天原始风险触发次数。
- 派生属性：统一按天级任务写入 `account_user_meta` 和 `account_user_meta_daily`。
- 陪伴类型：多标签 + 主类型 + 置信度 + 更新时间，按天级批处理，7 天重算一次。
- Admin 展示推断摘要，并支持人工覆盖陪伴类型。

### Phase 2：标签使用与运营增强

- 定义陪伴类型进入 prompt 的最小注入规则和置信度门槛。
- 增加 Admin 标签筛选、聚合分析和人工反馈入口。
- 处理用户明确纠正偏好后的标签降权、过期或重算策略。

### Phase 3：闭环优化

- 标签变更审计与回滚。
- 基于留存、安全风险和人工反馈优化陪伴类型判定。

## 10. 验收标准

- 同一环境中至少 2 个账号的元属性计算完全按 `account_id` 隔离，不串线。
- 新账号、0 消息账号、只有主动消息无用户回复账号的 `message_intensity_level` 均为 0。
- `message_intensity_level` 可通过 SQL 或单测验证：只统计截止昨日的用户入站消息，按 `floor(ln(1 + x))` 计算。
- 今日新增用户入站消息不影响当天已生成的 `message_intensity_level`，应在下一次每日更新后体现。
- 最近 30 天 safety 风险触发次数可验证：窗口外事件不计入，`pass` 不计入，同一消息多类别命中默认计 1 次。
- 派生用户标签数据按天级更新；当天新增消息、风险事件或陪伴类型信号不要求实时刷新 `account_user_meta`。
- 陪伴类型标签必须包含置信度、更新时间和过期或重算策略，不能只存一个永久枚举。
- Admin 默认只展示元数据和结构化标签，不展示聊天正文。
- Debug 账号在聚合分析中可排除，避免污染留存、消息强度和安全风险指标。
- 本期 schema 或 Admin 视图不新增生命周期分层、回复风格偏好、话题兴趣、主动触达反馈、权益增长反作弊、记忆上下文健康等已裁掉属性。

## 11. 风险与待确认

- `message_intensity_level` 的日界线是否统一使用服务默认时区，建议先按 `Asia/Shanghai`。
- `floor(ln(1 + x))` 是否满足运营展示直觉；如果后续 BI 需要其他分桶，可在展示层单独处理。
- safety event 的统一来源表和去重 key 需要在技术设计中明确，避免重复计数。
- 陪伴类型命名是否仅内部使用，还是未来会部分用户可见。
- `romance_roleplay` 是否需要更严格的年龄确认或开关策略。
- 推断标签是否允许进入 prompt；如果允许，需要定义 token 预算和注入优先级。
- 用户删除记忆或关闭个性化时，陪伴类型标签如何清理、降权或停止使用。
