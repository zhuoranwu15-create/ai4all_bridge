## 0. 一句话定位

朝夕用户可在个人中心创建一个由“名字、性格、使命、开场白”组成的 AI **角色模板**，审核通过并生成
公开的一句话简介后发布专属邀请链接；
新用户经链接首次加入朝夕时，系统才从模板快照实例化其自己的 AI 角色，
同时计入创建者的拉新关系。

## 1. 背景

当前系统已有两条独立能力：

1. 用户个人中心可取得个人邀请码及 `?invite_code=...` 注册链接。新用户首次加入朝夕时创建
   邀请关系，后续满足“绑定 + 3 条有意义消息”等条件后，邀请人按现行规则获得拉新奖励。
2. 运营可在后台创建 `?campaign_code=...` 营销活码，并绑定 AI 名字、SOUL 人设、使命和
   onboarding 引导语。新用户经活码注册后，账号保存策略快照并在 onboarding 应用指定角色。

本需求不是合并或废弃上述两套归因，而是在用户个人中心新增一个受控的“角色模板邀请链接”产品层：

```text
创建者的个人邀请码 + 创建者拥有的角色模板活动码
                    ↓
https://ai4company.top/?invite_code=<个人邀请码>&campaign_code=<角色模板活动码>
                    ↓
新用户首次加入朝夕
├─ 建立 referral 邀请关系：用于拉新归因与奖励
└─ 从模板版本生成实例化快照：写入新用户自己的 AI 内核
```

## 2. 产品目标

- 让普通朝夕用户无需运营协助，即可创建和分享 AI 角色模板。
- 明确区分模板与实例：创建/发布模板本身不产生可聊天 AI，只有新用户首次注册才实例化归其所有的角色。
- 一条链接同时兑现两件事：创建者获得拉新归因，新用户获得模板承诺的角色体验。
- 复用现有个人邀请码奖励规则，不新增一套平行奖励或重复发奖逻辑。
- 复用现有活动码注册参数和模板实例化快照思路，但补齐用户资产所有权、版本、审核和管理边界。
- 保持账号隔离：分享的是角色模板，不是创建者自己的 AI 实例或关系数据。
- 每位创建者最多同时持有 3 个角色模板，控制用户生成配置的管理和审核成本。

## 3. 非目标

- 本期不做公开角色市场、角色搜索、排行榜、交易、分成或付费售卖。
- 本期不允许创建者编辑底层 system prompt、工具、技能、模型参数或安全规则。
- 本期不允许创建者查看、接管或参与被邀请人的对话。
- 永远不允许创建者把角色模板“切换到”或覆盖自己的当前 AI；这不是未来版本待开放项。
- 不把创建者已有 AI 的 SOUL、IDENTITY、记忆或使命进度一键复制为模板。
- P0 不提供创建者试玩、角色调试、临时账号或预览对话，也不提供内部隐藏入口。
- 若创建者需要验证模板实际表现，必须发布后使用一个尚未加入朝夕的新账号通过该注册链接完成真实注册测试；
  该账号按真实用户处理，不是自动销毁的测试数据。
- 本期不允许新用户注册后用链接覆盖一个已经存在的朝夕 AI 账号。
- 本期不改变现有拉新达标、审核、风控和贝壳奖励规则。
- 本期不替代运营营销活码；运营活码仍由后台创建和管理。

## 4. 术语与对象

| 术语 | 定义 |
| --- | --- |
| 创建者 | 已登录个人中心、创建并分享角色模板链接的朝夕用户 |
| 角色模板 | 创建者填写的 AI 名字、性格/底色、使命、开场白，以及系统生成的版本、公开简介和审核状态；本身不是可聊天账号 |
| 模板版本 | 一次完整的名字、性格/底色、使命、开场白和系统生成简介组合；审核和发布都以确切版本为单位 |
| 开场白 | 被邀请人回复自己的称呼后，角色用于结束 onboarding、开始正式相处的首段角色化话术 |
| 一句话简介 | 模板内容审核通过后由 LLM 生成的公开展示摘要；包含角色名字，建议 10–20 个字。创建者可在发布前提交一次修改，修改内容需再次通过 LLM 安全审核 |
| 角色实例 | 新用户注册时从模板版本快照生成、归新用户所有的 AI；拥有独立会话、记忆和关系状态 |
| 角色模板活动码 | 系统为一个角色模板生成的 URL-safe 唯一码，主要作为链接内部参数 |
| 角色模板邀请链接 | 同时带创建者 `invite_code` 和模板 `campaign_code` 的朝夕官网注册链接 |
| 模板实例化快照 | 被邀请人建号时保存的模板版本；之后模板编辑或链接下线不追改已有角色实例 |

“角色创建者”只是模板资产的 owner，不是被邀请人账号、AI、记忆或关系的 owner。

## 5. 用户与权限

### 5.1 创建者资格

首版只有同时满足以下条件的用户可创建角色模板：

- 朝夕产品 membership 为 active；
- 已有可用的个人邀请码；
- 账号未被禁用，且未命中禁止分享/拉新的风控状态；
- 已完成自己的首次聊天 onboarding。

创建者只能读取、编辑、发布、停用和查看自己创建的角色模板与链接。所有读写必须同时按
`app_id=zhaoxi` 和创建者的 `platform_user_id` 约束，不能仅凭活动码访问。

创建者对模板的 owner 权限不延伸到任何角色实例；即使实例由其模板生成，创建者也不能读取或控制。
同样，模板 owner 权限不允许把模板应用到创建者自己的默认关系账号。

### 5.2 被邀请人资格

模板实例化和拉新归因仅在被邀请人**首次创建朝夕 product membership / 默认关系账号**时消费：

- 全新手机号首次加入朝夕：可同时建立邀请关系和模板实例化快照。
- 已有平台真人、但首次加入朝夕：仍按产品级新成员处理，可同时归因。
- 已经加入朝夕的老用户再次打开链接：不得重建邀请关系，不得覆盖现有角色、SOUL、使命或记忆。

### 5.3 运营与管理员

- Admin / Staff 可查看全部用户角色模板链接的配置、状态、创建者和聚合数据，并可因违规或风险停用。
- Reviewer 是否参与角色内容复核沿用内容审核权限边界；Reviewer 不获得用户账号管理权限。
- 后台操作必须保留操作者、时间、原因和变更前后值，不直接静默修改用户内容。

## 6. 创建者端用户流程

### 6.1 入口

在现有个人中心“邀请好友”区域增加“创建角色模板”入口。进入后展示：

- 已创建角色模板列表；
- 每个模板的名字、审核/发布状态、更新时间和注册链接；
- 创建、编辑、发布新版、复制链接、复制分享文案、停用/启用入口；
- 与运营活码一致的聚合转化漏斗（仅限创建者自己的模板，见 §10）。

原有“纯邀请码注册链接”继续保留，用户可以选择分享默认朝夕体验，或分享某个自建角色模板。

### 6.2 创建角色模板

模板包含四个必填字段，每个字段都由创建者自由填写：

| 字段 | 用户理解 | 产品要求 |
| --- | --- | --- |
| 名字 | 这个 AI 叫什么 | 自由填写的短文本、单行；不得冒充平台官方或真实公众人物 |
| 性格 / 底色 | 它是什么样的人、如何理解世界、如何陪伴用户 | 自由文本，但受长度、内容安全和提示注入防护约束 |
| 使命 | 它为何存在、想和用户一起完成什么 | 自由文本；描述长期陪伴方向，不是可绕过权限的操作指令 |
| 开场白 | 用户告诉角色自己的称呼后，角色想对用户说的第一段话 | 自由文本；用于替换统一自我介绍和 1–4 破冰菜单，不支持变量、工具调用或权限指令 |

建议交互：

- 表单用示例解释“性格”“使命”和“开场白”的差异，避免用户把三者写成同一句营销文案。
- 提供创建者自己的内容预览，但不向创建者暴露最终 system prompt 拼装结果。
- 创建时由系统生成模板活动码，但只有模板首次发布后才生成可复制的有效注册链接；普通用户不手工指定 code。
- 每位创建者最多同时持有 3 个未删除模板；模板处于 draft、审核中、approved、active、rejected 或 disabled
  均占用一个名额。软删除后释放名额，但历史版本、归因和审计记录继续保留。

具体长度上限、敏感规则和允许创建数量在技术设计前确认，不能由前端单独定义。

创建模板时，创建者不直接填写公开简介。名字、性格、使命和开场白整体审核通过后，由 LLM 基于名字、性格和
使命生成默认`一句话简介`：

- 简介必须带角色名字，按产品默认语言生成，建议 10–20 个字；这是生成目标，不因标点或不同语言的字长差异机械拒绝；
- 当性格和使命信息不足以形成可靠概括时，允许直接使用角色名字作为简介，不编造未提供的身份、能力或经历；
- 简介只概括角色，不复述完整性格、使命或开场白，也不加入邀请人数、平台背书等无来源信息；
- 简介属于当前模板版本。创建者编辑任一角色字段形成新版时，审核通过后重新生成，新版发布前不影响旧版简介；
- 审核服务不可用、输出无法解析或生成结果未通过机械校验时，版本不进入可发布状态并允许重试；不得把未审核字段或失败输出公开展示。

默认简介生成后，在版本发布前展示给创建者，并提供**一次**人工修改和提交机会：

- 修改提交只包含目标版本和修改后的完整简介，不能同时修改名字、性格、使命或开场白；
- 服务端必须再次调用 LLM 审核修改后的简介，判断内容安全、冒充、提示注入、虚假能力或其他公开展示风险；
- 审核通过：保存修改后的简介并返回“修改成功”；该版本不再提供简介编辑入口；
- 审核不通过：不保存用户提交内容，继续保留 LLM 最初生成的默认简介，并返回“你修改的内容存在：{具体原因}”；
  该版本同样不再提供简介编辑入口；
- “具体原因”按产品默认语言返回用户可理解的展示文本；稳定审核类别码、API 错误类型和数据库枚举继续使用英文；
- 前端和服务端先校验简介非空、包含角色名字且满足长度/字符边界；未通过机械校验时不调用 LLM，也不消耗编辑机会；
- 审核调用超时、provider 异常或结果无法解析不应误判为内容风险，也不保存修改、不消耗编辑机会，允许创建者重试同一次提交；
- 新建下一模板版本时，由 LLM 重新生成该版本默认简介，并重新获得一次简介编辑机会；不得通过重复提交、并发请求
  或重放旧请求突破每版本一次的限制。

### 6.3 模板、版本和链接状态

建议状态模型：

| 状态 | 含义 | 链接行为 |
| --- | --- | --- |
| `draft` | 尚未提交/未生成可分享链接 | 不可注册使用 |
| `pending_review` | 等待 LLM 审核、审核超时或等待重试 | 不可注册使用；创建者可查看状态 |
| `approved` | 当前候选版本审核通过、尚未发布 | 可以发布；不能被外部注册链接消费 |
| `active` | 至少有一个正式发布版本 | 可分享；新用户使用当前 published version |
| `rejected` | 内容不通过 | 不可注册使用；向创建者给出可修改的规则类别，不泄露风控细节 |
| `disabled` | 创建者或运营主动停用 | 不再实例化新角色；已有角色实例不受影响 |

名字、性格/底色、使命、开场白四个字段在首次发布和每次编辑后都必须调用 LLM 审核。审核和简介生成采用 fail-closed：

- LLM 明确通过且一句话简介生成成功后，版本进入 `approved`，但不会自动发布或自动开始 360 天有效期；
- 明确不通过时进入 `rejected`，向创建者返回可理解的规则类别，不直接暴露审核 prompt 或风控细节；
- 审核超时、provider 失败或结果无法解析时保持 `pending_review` 并允许重试，不能默认放行；
- 平台确定性校验和硬规则先于 LLM，LLM 不能批准平台明确禁止的内容；
- Admin/Staff 保留停用和人工处置能力。是否给 Reviewer 增加人工复核队列在技术设计中按现有权限能力评估。

简介人工修改被拒绝时不改变角色四字段的审核结论，不把版本改为 `rejected`；版本继续保持可发布状态并使用
LLM 默认简介。只有名字、性格、使命或开场白本身审核不通过时，才按模板内容审核规则进入 `rejected`。

### 6.4 发布、编辑与版本

- 创建者可编辑名字、性格、使命、开场白；每次通过审核并生成简介的编辑形成新版本。
- 创建者对该版本默认简介的一次修改不创建新的模板版本；通过后只更新该版本的公开简介和简介审核审计字段。
- 审核通过的版本由创建者主动发布；P0 不提供发布前试玩或调试。
- 第一个 approved version 由创建者主动点击“发布”后成为 published version，模板进入 active；此刻才写
  `activated_at` 并从该时刻起计算 360 天。
- active 模板编辑后，候选版本审核通过进入 approved；旧 published version 继续服务。创建者主动“发布新版”后，
  新注册用户才切到新版本；发布新版不延长模板原有 360 天有效期。
- 新注册用户使用注册提交时的 published version 并保存实例化快照。
- 已经归因的账号继续使用原快照，不被创建者后续编辑、停用或删除追改。
- 编辑必须重新调用 LLM 审核；审核期间旧 published version 和旧链接继续可用，审核不通过或
  候选未发布都不污染旧版本。
- 删除首版采用软删除/停用语义，不物理删除已有归因和审计记录。
- 模板首次发布时确定 `expires_at = activated_at + 360 天`；后续编辑、发布新版、停用再启用不自动续期。
  到期后不再允许新用户消费模板，但已有角色实例继续使用注册时快照。

### 6.5 P0 不提供试玩与调试

- 个人中心不展示“试玩”“调试”“切换到该角色”或任何等价入口。
- 创建者审核通过后可以直接发布；页面明确提示：“当前暂不支持在线试玩。若需验证角色实际效果，请复制发布后的
  注册链接，使用一个尚未加入朝夕的新账号完成注册测试。”
- 用于测试的新账号必须满足 §5.2 的真实新成员条件，并完整执行 §7–§9 的注册、归因、onboarding、计费、记忆和
  生命周期规则；它不是测试沙盒，不会自动清理，也不能在测试后合并到创建者当前 AI。
- 若测试账号与创建者属于同一真人或命中自邀/反作弊规则，邀请奖励按现有规则拒绝或进入风控；角色模板是否实例化
  仍以服务端注册校验结果为准，不能为了测试绕过风控。
- 未来试玩必须重新立项，重新评估环境隔离、账号模型、计费、日志、数据清理和验证一致性；P0 不预留 trial 表、
  API、feature flag 或隐藏调试能力。

## 7. 被邀请人注册与 Onboarding 流程

### 7.1 落地页

用户打开角色模板邀请链接后，落地页应展示最小且真实的信息：

- “你将领取由某位朝夕用户创建的角色模板，并生成属于你的 AI 伙伴”；
- 模板名字和当前 published version 审核通过后生成的一句话简介；
- 邀请关系的通用说明；
- 不展示创建者手机号、内部 ID、邀请人数、被邀请人名单等隐私信息。

公开预览和注册落地页不得返回或展示完整性格、使命、开场白，也不得通过截断原文的方式生成摘要。
创建者本人和有权限的 Admin/Staff 仍可在各自受保护页面查看完整模板内容。

`invite_code` 和 `campaign_code` 均从 URL 静默带入注册请求；活动码不要求新用户手填。

### 7.2 注册成功时的双归因

对于首次加入朝夕的新成员，系统应完成以下两条业务结果：

1. 校验创建者个人邀请码，建立现有 `referral_relationship`，按当前规则累计邀请码使用次数。
2. 校验模板活动码的状态、owner 和 published version，给新建的 AI 账号写入模板实例化快照。

用户角色模板活动码必须与同一链接里的个人邀请码属于同一创建者。若攻击者手工拼接甲的邀请码和乙的
模板码，不得形成“甲拿奖励、乙提供模板”的混合归因。

两条记录用途不同：

- referral 绑定 `inviter_platform_user_id ↔ invitee_platform_user_id`，服务拉新审核和奖励；
- 模板实例化归因绑定被邀请人的 `account_id`，服务名字、性格、使命、开场白和 onboarding。

### 7.3 Onboarding 行为

角色模板链接有效且双归因成功时：

- AI 名字直接使用角色模板的名字；
- SOUL/人格直接使用角色模板的性格；
- 使命直接使用角色模板的使命；
- 开场白使用注册时 published version 的开场白快照；
- 自由使命只作为稳定的 `MISSION` prose 影响 AI 行为，不产生目标数、瞬间记录、进度状态或使命工具，
  也不再额外哈希分配一个系统量化使命；
- onboarding 只询问被邀请人的称呼，不再询问 AI 名字或人设；
- 跳过“给 AI 起名”和“选择 AI 人设”的默认步骤，避免覆盖链接承诺的角色；
- 用户第一次发消息时，系统仍在当前回复中自然回应并询问用户称呼；
- 用户回复称呼后，角色使用该版本的开场白完成 onboarding。该轮不得再输出默认自我介绍或 1–4 编号破冰菜单；
- 如果本轮没有可靠提取到用户称呼，也不再进入 AI 名字/人设选择，仍使用开场白完成 onboarding；后续对话若自然获得称呼，按现有规则写入 `USER.md`；
- 开场白是已审核的角色内容，不作为高优先级指令，不支持占位符插值，也不能要求调用工具或突破平台规则；
- 从第一条模型生成的回复起使用该角色的名字、性格和使命；自定义开场白只用于上述 onboarding 收尾轮；
- onboarding 完成后，后续记忆、关系阶段、使命进度完全属于被邀请人的独立账号。

角色性格和使命必须以受控资产进入 prompt，不能把用户自由文本当成具有更高优先级的系统指令；
平台安全规则、工具权限和产品约束始终优先。

## 8. 归因优先级与异常规则

| 场景 | 注册 | 拉新归因 | 模板实例化 | 用户提示 |
| --- | --- | --- | --- | --- |
| 两个码均有效且 owner 一致 | 成功 | 创建 | 创建角色实例快照 | 展示模板将生效 |
| 邀请码有效，模板码超过 360 天有效期/停用/不存在 | 可继续 | 创建 | 不创建，按无预设走普通新用户 onboarding | 明确提示模板不可用，不能静默承诺已生效 |
| 邀请码无效，模板码有效 | 按现有邀请码注册策略处理；新成员不得只靠该组合绕过 | 不创建 | 不创建 | 提示邀请链接无效 |
| 两个码 owner 不一致 | 可按有效邀请码继续默认注册 | 可创建 | 不创建 | 明确提示模板不可用；记录异常 |
| 已是朝夕成员 | 正常登录 | 不新增 | 不覆盖 | 提示链接仅对首次加入用户生效 |
| 创建者自点自己的链接注册 | 按现有防自邀规则拒绝邀请归因 | 不创建 | 不创建 | 提示不能邀请自己 |
| 模板编辑/停用发生在注册过程中 | 以服务端提交时校验到的 published version 为准 | 按邀请码结果 | 成功则落版本快照，否则默认角色 | 不展示过时承诺 |

角色模板活动码失效不阻断真实注册：保留有效个人邀请码的拉新归因，把被邀请人视为“没有角色预设”的
普通新用户，完整执行默认 onboarding。落地页或注册结果必须清楚说明角色没有生效，不得继续展示
“将使用该角色”的过时承诺。邀请码是否阻断注册继续遵循当前 `open | invite_only | closed` 策略。

## 9. 拉新奖励规则

- 角色模板邀请链接不新增奖励类型，直接复用个人邀请码的拉新关系和现行奖励规则。
- 被邀请人仍需完成绑定并满足当前“3 条有意义消息 + 审核/风控”条件，创建者才获得奖励。
- 一个新成员只建立一个可奖励的朝夕邀请关系；不能因访问多个模板链接重复归因或发奖。
- 模板活动码的使用次数不能替代拉新成功数；“从模板实例化角色”和“拉新达标发奖”是两个指标。
- 创建者个人邀请码被禁用或受风控限制时，其模板链接也不能绕过邀请限制。

## 10. 数据可见性与统计

创建者端首版统计范围与当前运营活码统计对齐，但每个创建者只能查询自己拥有的模板码：

- 聚合阶段：曝光 PV、曝光 UV、注册、扫码、激活、onboarding step1、step2、完成；
- 聚合转化率：访问→注册、注册→扫码、注册→onboarding 完成；
- 时间维度：汇总值和按北京自然日分桶的每日数据；默认最近 14 天，单次查询最长 92 天；
- 模板审核/发布状态、累计实例化次数和有效期等配置摘要。

如果运营活码统计口径后续增加或减少字段，创建者端原则上同步；若发现隐私、反作弊或产品误导风险，
再单独收紧并记录差异。当前这些指标均为聚合数据，不包含逐个被邀请人明细。

不得向创建者展示被邀请人的手机号、账号 ID、微信标识、聊天内容、记忆、审核理由、风控标签或名单。
运营后台仍可按现有权限查看完整聚合漏斗、异常组合次数和审核状态；查看任何用户级信息继续遵循
现有 Admin 隐私与审计规则。

## 11. 内容安全与滥用防护

用户创建的模板性格和使命会影响模型行为，属于高风险的用户生成配置，最低要求：

- 服务端校验字段长度、字符和结构，前后端规则一致；
- 名字、性格/底色、使命、开场白在发布和编辑时均调用 LLM 审核，并保留审核状态、模型、结果类别、时间和
  可审计摘要；
- 审核 System prompt 整体按产品注册表的 `default_language` 选择对应语言版本；审核类别码、字段名和
  API/数据库协议继续使用稳定英文；
- 审核默认通过，只有明确且实质命中安全风险时才拒绝。与真实人物或影视、动画、游戏、文学角色重名或相似，
  以及对虚构作品的提及、致敬或启发，本身不属于内容安全拒绝理由；著作权、商标和角色 IP 相似不在本次
  内容安全审核范围内；
- 正常的角色设定指令不视为提示注入；`other_unsafe_content` 不能作为“不确定”或主观不适的兜底拒绝类别。
  内容存在多种合理解释、且没有明确证据支持危险解释时应通过；
- 公开一句话简介默认只能从审核通过的名字、性格和使命生成；创建者提交的替换简介必须另行通过安全审核。
  两种来源都禁止直接截断并公开原文，也禁止包含无来源的身份或能力；
- 审核禁止违法、仇恨、色情剥削、自残诱导、诈骗、冒充官方或真实个人等内容；
- 防止提示注入：模板文本只能描述人格与使命，不能提升工具权限、泄露系统 prompt、读取其他账号数据
  或覆盖安全规则；
- 创建、编辑、审核、启停和管理员处置均有审计记录；
- 对创建频率、active 链接数量、短时注册量设置产品级限额和风控；
- 被举报或命中高风险时可立即停用新注册入口，但不能破坏已有用户账号的一致性；已有账号是否需要
  安全替换角色，必须走单独的安全处置流程并留痕，不能由创建者远程修改。

## 12. 账号隔离与生命周期不变量

- 角色模板归创建者的 `platform_user_id + app_id=zhaoxi` 所有；模板不能跨产品使用。
- 同一创建者最多持有 3 个未删除模板，服务端在并发创建时也必须保证不能突破上限。
- 模板实例化快照、开场白快照和最终 profile/SOUL/使命归被邀请人的 `account_id` 所有，所有读写必须带 `account_id`。
- 被邀请人的会话、记忆、关系状态、使命进度、权益和主动消息均从空白独立生成，不复制创建者数据。
- 创建者停用或注销时，链接停止接受新归因；已有被邀请人的角色实例快照继续存在。
- 模板首次发布后有效 360 天；到期只影响后续注册，不删除模板、统计或已有账号快照。
- 创建者当前 AI 永远不读取或应用其创建的模板；P0 不提供试玩、调试、切换或临时账号路径。
- 创建者为验证效果而使用链接注册的新账号是普通真实账号，归测试账号所有，按正常生命周期运行和保留。
- 被邀请人后续能否自行改名、调整性格，沿用朝夕现有 onboarding 后的人格变更规则；创建者没有远程锁定权。
- 账号注销和数据删除按各自 owner 处理：删除创建者不能连带删除被邀请人账号，删除被邀请人也不能删除
  创建者模板和聚合计数所需的合规记录。

## 13. 与现有能力的关系

### 13.1 个人邀请码

继续复用现有个人码“一位用户、一个朝夕 personal code”的模型。不同模板链接可共用创建者的同一
个人邀请码；每个模板拥有不同活动码，因此可区分模板转化，同时所有合格拉新归到同一创建者。

### 13.2 运营营销活码

运营活码与用户角色模板码可继续共用 `campaign_code` URL 参数和归因管道，但必须在资产所有权、创建入口、
可编辑字段和权限上区分：

- 运营活码由 Admin/Staff 创建，可配置运营预设和营销话术；
- 用户模板码由登录用户创建，只允许配置名字、性格、使命、开场白，不开放其他营销话术和底层策略字段；
- 用户模板码必须有 creator owner，并与链接邀请码做 owner 一致性校验；
- 后台不得把运营码误显示在用户个人中心，也不得让用户读取或编辑他人角色码。

### 13.3 模板实例化与角色运行时

当前营销活码只能引用工程注册的 `soul_preset_key` 和 `mission_id`。本需求允许用户自由填写性格和使命，
因此实现时必须引入受控、可版本化的角色模板资产，并把 published version 渲染为被邀请账号的实例化快照。
不能把任意自由文本伪装成现有静态 preset ID，也不能把它直接拼成高优先级 system prompt。

自由使命在 P0 是稳定 prose：写入被邀请账号的 `MISSION.md`，但不写现有结构化 `account_mission`，
不开放 `mission_status` / `record_mission_moment`，并阻止 onboarding 完成时再分配一个默认量化使命。

## 14. 分期建议

### P0：可用闭环

- 个人中心入口、角色模板创建/编辑/审核/发布/停用和模板列表；
- 名字、性格、使命三字段及服务端校验；
- 三字段 LLM 审核、失败关闭、重试和审核审计；
- 每位创建者最多 3 个模板，模板首次发布后有效 360 天；
- 系统生成模板活动码和双参数链接；
- owner 一致性校验；
- 新成员双归因、模板版本实例化快照和 onboarding 强制角色；
- 明确的“P0 暂不支持在线试玩；请用全新账号通过发布链接完成真实测试”提示；
- 账号隔离、内容安全、基础限额和 Admin 停用；
- 与运营活码一致的完整聚合漏斗展示。

### 当前增量：自定义初见体验与最小公开展示

- 创建表单增加开场白，和名字、性格、使命一起版本化、审核与发布；
- 有效模板 onboarding 只问用户称呼，称呼回复后用开场白替换默认自我介绍和 1–4 破冰菜单；
- 审核通过后由 LLM 生成带名字的一句话简介，建议 10–20 个字，内容不足时可只使用名字；创建者可在发布前修改并提交一次；
- 人工修改通过安全审核后保存；未通过时保留默认简介、展示具体原因并关闭该版本的简介编辑入口；
- 公开预览只展示角色名和一句话简介，不再暴露性格、使命或开场白全文；
- 旧 published version 和已实例化账号保持原快照，不调用 LLM 批量改写历史版本；缺少公开简介的历史版本公开展示回退为角色名，
  缺少开场白快照的历史账号继续使用原 onboarding 收尾逻辑。

### P1：运营与增长增强

- 更完整的访问→注册→绑定→onboarding→拉新达标漏斗；
- 分享卡片、角色预览页和更丰富的分享文案；
- 角色模板草稿、复制和更多官方引导模板；
- 用户举报、申诉和更细的审核工作台。

### V2 候选：创建者试玩

- 只有当真实测试成本已明显影响模板创建/发布转化，或用户需求量达到重新立项标准时再评估。
- 重新立项时先确认环境隔离、账号模型、计费、日志和数据生命周期，再决定采用何种实现；不继承 P0 的技术假设。

## 15. 验收标准

- 合格创建者能在个人中心创建含名字、性格、使命、开场白的角色模板，审核并生成一句话简介后主动发布，并获得由系统
  生成活动码的专属链接；服务端必须校验活动码 owner 与个人邀请码 owner 一致。
- 链接同时带创建者个人邀请码和该模板活动码，刷新、登录、OTP、扫码链路不会丢失任一参数。
- 全新朝夕成员经有效链接注册后，只创建一条邀请关系，并保存一份对应模板 published version 快照。
- 被邀请人的 AI 从首个模型生成回复起使用指定名字、性格和使命，onboarding 不再要求其给 AI 起名或
  重新选择人设；用户回复自己的称呼后，以注册时开场白快照收尾，不展示默认自我介绍和 1–4 破冰菜单。
- 有效链接的公开预览只返回角色名、当前审核通过的一句话简介和必要有效期信息，不返回性格、使命、开场白全文。
- 一句话简介包含角色名、建议 10–20 个字；性格和使命信息不足时允许等于角色名，不得编造未提供的设定。
- 创建者能在版本发布前看到默认简介并提交一次修改；通过时保存修改，拒绝时保留默认简介并返回按产品语言展示的
  具体风险原因。无论通过或拒绝，该版本均不能再次编辑简介，并发或重放也不能突破限制。
- 被邀请人的 Soul、使命、会话、记忆、权益和关系状态与创建者及其他被邀请人完全隔离。
- 创建者编辑或停用模板后，已有被邀请人保持注册时角色；后续新用户使用当前 published version 或按失效规则
  回退，不发生半新半旧配置。
- 同一老用户重复打开链接不会新建邀请关系、重复计数或覆盖现有角色。
- 活动码和邀请码 owner 不一致时不应用角色，并记录可观测异常。
- 模板码失效但邀请码有效时，注册可按现有策略继续，拉新归因保留，且用户明确知道模板未生效。
- 邀请奖励仍只按现有有意义消息、审核、风控和幂等规则发放，不因模板活动码重复奖励。
- 创建者只能管理自己的模板，且只能看到聚合转化数据，无法看到被邀请人的身份和对话数据。
- 创建者最多同时持有 3 个未删除模板，并发创建也不能突破；软删除后释放名额。
- 四字段创建和编辑提交均经过 LLM 审核；简介生成失败或审核失败/超时不会放行未审核版本，编辑审核失败不影响旧
  published version。
- 模板从首次发布起有效 360 天，编辑、发布新版或停用再启用不续期；到期后新用户走普通 onboarding。
- 创建者当前 AI 在创建、编辑、发布和删除模板前后均不被覆盖、不应用模板、不改变任何状态。
- P0 页面和 API 均不存在试玩、调试、切换、临时账号或隐藏入口；发布完成后清楚提示需用全新账号通过注册链接测试。
- 测试新账号完整走真实注册/归因/onboarding，作为普通账号长期保留并进入正常统计和风控；不得标记成临时数据或
  在后台自动删除。
- 创建者能查看与运营当前一致的 PV/UV、注册、扫码、激活、onboarding 和转化率聚合统计，但不能
  越权查询其他创建者的角色码。
- Admin/Staff 可停用违规模板并看到审计记录；平台安全规则始终高于用户模板文本。
- SQLite 与 PostgreSQL 路径对 owner 隔离、双归因、版本快照和并发幂等行为一致。

## 16. 已确认决策（2026-08-01）

| 问题 | 决策 |
| --- | --- |
| 模板字段 | 必须包含名字、性格/底色、使命、开场白四个字段，每个字段内由创建者自由填写 |
| 自定义开场白 | 用户回复称呼后替换默认自我介绍和 1–4 破冰菜单 |
| 公开一句话简介 | 创建时不直接填写；四字段审核通过后由 LLM 基于名字、性格、使命生成，必须带名字，建议 10–20 个字，信息不足时可直接使用名字 |
| 简介人工修改 | 每个未发布版本一次机会；通过安全审核则保存，拒绝则保留默认简介并展示具体原因；两种结果都关闭该版本的编辑入口 |
| 公开展示边界 | 只展示角色名和一句话简介；不展示性格、使命、开场白全文，也不截断原文充当摘要 |
| 内容审核 | 创建和每次编辑提交均调用 LLM 审核，未通过或调用失败不放行新版本 |
| 创建上限 | 每位用户最多同时持有 3 个未删除角色模板 |
| 链接有效期 | 360 天 |
| 模板失效 | 不应用预设，按普通新用户执行完整默认 onboarding；有效邀请码仍保留拉新归因 |
| 创建者统计 | 首版与运营活码当前可见聚合统计对齐，后续发现问题再收紧 |
| 自由使命语义 | 只作为稳定使命 prose，不增加目标数、瞬间记录、进度状态或使命工具 |
| 名额释放 | 最多同时持有 3 个未删除模板；soft delete 释放名额，其他状态仍占名额 |
| 有效期起算 | 第一个版本 LLM 审核通过并由创建者首次主动发布激活时起算；后续发布新版不续期 |
| 创建资格 | 已完成 onboarding、账号 active 且无风险限制的用户；灰度期可再加白名单 |
| 活动码展示 | 默认只显示和复制完整链接，不强调原始活动码；排障时可展示 |
| 编辑影响范围 | 不影响老用户，只对之后注册的新用户生效，老用户保留快照 |
| owner 不一致 | 不应用角色；有效邀请码可继续默认注册，同时记录异常 |
| 首次聊天 | 用户第一条消息的回复仍询问用户称呼；用户回复后使用模板开场白完成 onboarding |
| 角色邀请奖励 | 不新增，完全复用现有个人邀请码奖励 |
| 领域对象 | 创建者创建的是角色模板；新用户注册时才产生独立角色实例 |
| 创建者切换 | 永远不能把模板切换到或覆盖创建者当前 AI |
| P0 试玩/调试 | 不支持；不创建 trial Runtime Account，不预留隐藏入口 |
| 测试方式 | 发布后复制注册链接，使用一个尚未加入朝夕的新账号完成真实注册测试 |
| 测试账号性质 | 普通真实账号，正常保留并进入注册、归因、onboarding、计费、统计和风控规则 |

## 17. V2 试玩候选边界

试玩不属于本 PRD 的 P0/P1 承诺，也不属于当前技术设计的预留能力。后续只有在需求量、真实测试成本或发布转化数据
证明值得投入时重新立项；届时重新比较独立环境、账号/会话模型、计费、日志、数据删除和效果一致性，不默认沿用
任何“在生产主库创建临时账号再删除”的方案。

对应技术方案见
[用户自建角色模板与邀请链接技术设计](../../../architecture/products/zhaoxi/creator_role_template_referral_link_technical_design.md)。
