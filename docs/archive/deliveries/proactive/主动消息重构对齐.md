# 主动消息（app/proactive/）重构对齐

> 临时跟踪文档，用于团队同步主动消息这块的代码重构进度、决策与 bug 状态。
> 阶段1 完成、整理稳定后可归档到 `docs/archive/`。
> 完整设计见各阶段下文；原始评审结论由本文档承载，无需翻聊天记录。

## 背景

`app/proactive/`（13 文件 / ~4400 行）承载主动消息全部业务：**生成候选 → 策略闸门 → 出站发送**。
评审发现两类问题：

- **结构**：`account_checks.py`(950) / `reactivation.py`(904) 是 god-file；4 段 system prompt 内联在业务代码；
  编排器 `scan_due_proactive_account_checks` 错放在 `state.py`；"候选"概念有 5 种存法。
- **正确性 bug B**：reactivation 自身 avoidance 窗口（60min）与 policy 对 companion_followup 的 avoidance 窗口（6h）
  口径不一致，候选被 policy 取消后既不清也不改期 → 每 tick 空转、卡到次日。

## 总体策略（已确认）

- **深度 = 外科式整理**：行为零变更，旧模块路径做"门面再导出"，对外 import 全部不变。
- **顺序 = 阶段0 先单独修 bug（独立 PR）→ 阶段1 结构整理（独立 PR）**。
- **account_check 休眠路径 = 保持 admin-only，仅补文档**（产品有意设计，零行为变更）。
- 不引入新依赖；账号隔离不变量不受影响。

## 阶段0 详情

### 0.1 bug B — reactivation 候选被 policy 取消后空转
- **根因**：`dispatch_reactivation_candidate`（`reactivation.py`）只在 `sent` 时清候选；`cancelled` 既不清也不改期，
  `scheduled_at` 停在过去 → 每 tick 重复评估 + 重跑 policy；planning 见 pending 候选不重规划 → 卡到次日。
- **修复**：给 `outbound_status == "cancelled"` 加显式分支——`_next_slot_after` 有下一 slot → `reschedule`（reason
  `send_blocked_policy`）返回 `delayed`；无 slot → `clear`（reason `send_blocked_policy_final_slot`）返回 send_blocked。
  把每-tick 空转降为每-slot 重试（无窗口下当天最多 3 次后清除，等下次 planning 重新生成）。
- **不动**：policy、`_avoidance_count` 口径（两 knob 语义不同，刻意保留）；`failed` 等其它状态维持原 `send_blocked` 行为。
- **测试**：`tests/test_reactivation.py` 新增——policy 取消时断言 `delayed` + `scheduled_at` 前移、第二 tick 不再立即 due；末位 slot 时断言候选清除。
- **已知次要遗留**：当账号设了 allowed_windows 时 `_next_slot_after` 恒返回未来 slot（不返回 None），若 policy 永久拦截
  （如 master 关闭）候选不会经此路径清除，只会被每 slot 重试一次——仍远好于每 tick；彻底清理留作后续。

### 0.2 bug A — account_check 休眠路径（仅文档）
- **结论**：account_check candidate **仅由 admin 端点** promote 产生（`admin_proactive.py`），自动调度不生成，
  故 scheduler 的 account_checks 步在无人工候选时恒 `no_op`。这是有意设计。
- **动作**：`scan_due_proactive_account_checks` 与 `account_checks.py` 模块 docstring 各加一句说明。零行为变更。

## 阶段2 详情 — 推荐器 seam（自主外联族，行为等价）

### 决策（已确认 · 第二轮）
- **覆盖范围 = 仅自主外联族**：`topic_followup` / `content_invitation` / （admin）`manual_companion` 走"召回→排序→选择"；
  `reminder` / `commitment` 属"义务型"，时间锚定直发，**不纳入**。
- **全局召回 = 协议先到位、实现留 stub**（Q1）：`Recaller` 协议本轮带上 `scope=account|global` 维度；真正的全局
  recaller（如热点话题扇出+跨用户去重）**需跨账号候选池，等阶段3 表落地再接**。本轮不建表、行为等价。
- **account_check = 更名归位、仍 admin-only**（Q2）：消除"一个词背三件事"的语义混乱，零行为/产品变更。
- **存储层 = 本轮按职责重切 + 门面**（Q3）：`reactivation.py` 拆成 store/scheduling/dispatch 三层职责，退为门面；
  对外 `from app.proactive.reactivation import …` 全不变。`reactivation` 退回为"候选 kind 分组 + 产品目标"，不再当层名。
- 仍**不建候选池表**；账号隔离不变量不受影响。确立"召回 ↔ 选择 ↔ 存储 ↔ 调度 ↔ 派发 ↔ 发送"全切割面，
  为阶段3（`proactive_candidates` 表 + 真·全局召回）/ 阶段4（真实排序信号 + 生成拆进程/仓）打地基。

### 现状基线（要形式化的"隐式选择"）
`plan_reactivation_candidate`（`reactivation.py:410`）= 固定优先级选择器：topic_followup 命中即用（优先级1），
否则 content_invitation（`action=="content_invitation_candidate_created"`，优先级2），都空 → no_op
（reason = `content_result.reason or topic_result.reason or "no_reactivation_candidate"`）。

## 阶段2.5 详情 — 包重组 + 退门面（行为等价，纯搬家）

针对"后半段一堆平级文件"的批评，按**职责分子包**，并退役两个门面。

### 目标结构（依赖单向向下、无环）
```
contract/     candidate · categories · prompts · common      纯·无 I/O（候选类型从 selection 上提）
recall/       (原 generation/) base(Recaller) · topic_followup · content_invitation · manual_companion · _shared
selection/    ranker · selector                              纯机制
store/        candidates(原 candidate_store) · account_state(原 state)   持久化 I/O
slots.py      (原 scheduling.py)                             算几点发（send slot 计算）
delivery/     outbound(原 messaging) · policy · dispatch(原 dispatch/outreach) · account_check   闸门+发送（共享地板）
obligations/  reminders · commitments · content_invitations  义务型（只落 delivery）
orchestration/ planning · scheduler                          编排
preferences.py (原 settings.py)                              偏好解析（跨切，避免 policy↔scheduling 环）
```

### 对四点批评的落地
- **存储 vs 数据**：候选**类型** `ProactiveCandidate` 上提到纯 `contract/`；候选**存储**（I/O）独立为 `store/`，不污染纯层。
- **调度/派发/闸门/发送/编排重组**：`delivery/`（outbound+policy+dispatch）收编飘着的 policy；`preferences` 抽出破环；`orchestration/` 收编 scheduler+planning。
- **义务型强插**：`obligations/` 只向下够到 delivery（+ 一个 account_state 标记），不穿透 recall/selection/scheduling。
- **门面退役**：删除 `reactivation.py` / `account_checks.py`；~40 处 import 改指真实模块，15 处 `patch()` 目标 repoint 到真实模块。

### 验证
全量 **971 passed**；`import app.main` 无循环 import；pyflakes 仅 1 处 pre-existing 未用 re-export（`delivery/outbound.py` 的 `is_quiet_hours`，重组前既有）。33 个 app/proactive 文件搬家、66 文件总改动，行为零变更。

### 命名去重（scheduler/scheduling/planning 撞车）
`scheduling.py` 与 `orchestration/scheduler.py` 是近义同根词却指两事，故：
- `scheduling.py` → **`slots.py`**（算几点发）；三词各归其义：scheduler=跑循环、planning=规划发什么、slots=算几点发。

- 全量 971 passed；pyflakes clean。

## 阶段3 详情 — 全局召回落地：近期热点 (hot_topic)

第一个**真·全局召回**：搜索近 24h 热点 → 抽主题成无主候选池 → 每账号 LLM 打分选择/排序 →
多样性打散 → top1 写回该账号单条 `reactivation_candidate` → 复用既有 dispatch/policy/去重发送。
兑现阶段2 埋的 `scope=global` 契约。

### 决策（已确认）
- **全局池 = 新建 `proactive_global_candidates` 表**：正式跨账号池 + 24h TTL + 历史去重基线，后续更多全局召回复用。
- **每账号选择 = LLM 相关性打分**：喂 `MEMORY.md`(长期记忆) + 近 50 条聊天 + 主题池 → 返回 top-N 及分数/理由（profile 建成前的近似）。
- **policy 分类 = 复用 `companion_followup`**：不加新配额 knob / 用户设置项；`hot_topic` 仅是新的**候选 type**，产品目标仍是拉活陪伴。

### 账号隔离（关键自审）
- `proactive_global_candidates` 是**唯一刻意无 `account_id` 的表**——存的是"无主候选池"（所有账号只读共享的灵感来源），不是任何账号的数据。**必须在建表迁移与 store 模块 docstring 显式标注为隔离不变量的例外**。
- 一切**每账号**读写仍严格按 `account_id` 约束：LLM 打分只喂该账号自己的记忆/聊天；选中的 top1 只写进该账号自己的 `proactive_account_state.metadata.reactivation_candidate`；发送/去重/配额沿用既有 account 维度路径。池 → 账号的落点由选择层"盖 account_id"这一步完成，无跨账号泄漏。

### 分层落地（沿现有 contract/recall/selection/store/delivery/orchestration 切面）

**3.1 store —— 全局池表**
- `_core.py` `_MIGRATIONS` 追加一个迁移函数：建 `proactive_global_candidates(id, kind, topic, text, generated_date, dedupe_key, expires_at, metadata, created_at)`，`UNIQUE(kind, generated_date, dedupe_key)` 天然做当日+历史去重。
- `app/db` 加访问函数：`insert_global_candidate` / `list_active_global_candidates(kind, now)`（未过期池）/ `list_recent_global_candidate_keys(kind, since)`（历史去重依据）。
- `store/global_candidates.py`：薄封装 + normalize + `dedupe_key` 归一化（复用 `_normalize_dedupe_key` 口径）。

**3.2 recall —— 全局召回（scope=global，每日一次）**
- `recall/hot_topic.py::refresh_hot_topic_pool(*, now)`：门控 `hot_topic_recall_enabled`(默认 False，fail-closed) + `is_llm_configured` + `web_search_enabled`；直接调 web search（近 24h 热点 query，**不走 TurnContext 工具循环**，避免全局无账号取 ctx 的坑）→ `generate_completion` + `HOT_TOPIC_RECALL_SYSTEM_PROMPT` 抽 N 条主题（topic + 可直接发送的通用 hook 文案）→ 用 `list_recent_global_candidate_keys` 滤掉近 N 天已用主题 → 幸存者入池（TTL=now+`hot_topic_ttl_hours`）。幂等：当日池已在则 no_op。

**3.3 selection —— 纯排序 + 多样性打散**
- `selection/diversity.py`（纯函数、零 I/O、可单测、未来复用）：`rank_and_diversify(scored_items, recent_topics, *, top_k, penalty)` —— 按分排序取 top_k，对 topic 命中"近 3 次已发"的项降权后置。

**3.4 recall —— 每账号 LLM 打分选择 + 个性化改写（scope=account）**
- `recall/hot_topic.py::select_hot_topic_candidate(*, account_id, now)`：guard 与 topic_followup 对齐（账号 active / state enabled / llm / route）；读全局池，空则 no_op；读 `MEMORY.md` + 近 50 条 → `HOT_TOPIC_RANK_SYSTEM_PROMPT` 打分（返回 `[{id, score, reason}]`）→ `rank_and_diversify`（recent_topics 取近 3 次已发拉活）→ top1。
- **个性化改写**：对选中的 top1 再走一次 LLM（`HOT_TOPIC_PERSONALIZE_SYSTEM_PROMPT`），结合该账号**人格 SOUL + 记忆 + 近聊**把池内通用 hook 重写成发给这个用户的口语消息；改写失败/空则回退通用 hook（不阻断发送）。原 hook 存入 `metadata.base_text`，`metadata.personalized` 标记是否改写成功。仅对 top1 一条做，不对整池。
- 组装成 `type=hot_topic` 候选 dict（形状对齐 `topic_followup_candidate_created` 返回），`text` 为个性化后的最终发送文案。

**3.5 orchestration —— 接入 planning**
- `selection/ranker.py`：`DISCRETIONARY_RANK` 追加 `"hot_topic"`（**末位 fallback**：topic_followup > content_invitation > hot_topic；顺序可后续按效果调）。
- `orchestration/planning.py`：`plan_reactivation_candidate` 增 `hot_topic_generator` 注入 + `_hot_topic_proposer`，注册进 `select_first`；末尾 no_op reason 回退链**泛化为按 rank 顺序遍历 outcomes**（不再硬编码 content/topic 两项）。`scan_due_proactive_account_checks` 传 `hot_topic_generator=select_hot_topic_candidate`。
- **短路语义不变**：topic_followup 命中则 hot_topic 不执行（与"高优先抢占"一致）。

**3.6 scheduler —— 每日刷新步**
- `ProactiveScheduler.run_once` 加一个隔离步 `refresh_hot_topic_pool`（与 `expire_content_invitations` 同级，单步失败不拖垮整轮）；幂等+门控，故每 tick 跑安全（当日池已在即 no_op）。admin run-once 端点手动触发调试。
