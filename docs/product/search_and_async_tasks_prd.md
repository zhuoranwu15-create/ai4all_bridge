# 产品专题 PRD：搜索与异步任务

更新时间：2026-05-26

## 1. 目标

让用户在微信中触发 Web Search、复杂资料整理、长内容生成等高耗时任务时，不需要长时间等待同步回复；系统先快速确认，后台完成后再补发完整结果。

Phase 1 中，搜索场景默认全部异步处理，不做同步搜索回复。

## 2. 用户流程

1. 用户在微信中触发搜索任务，例如“帮我查一下最近 XX 的消息”。
2. 系统先快速回复确认，例如“我先帮你查一下，整理好后发你。”。
3. Backend 创建异步任务，记录任务状态、触发消息、账号、会话、工具输入和幂等键。
4. Worker 执行 Web Search、内容筛选、摘要和最终回复生成。
5. 任务完成后，通过 OpenClaw Gateway send 主动补发完整结果。
6. 如果任务失败或超时，系统补发简短失败说明，并可建议用户换个问法。

## 3. 功能需求

- 支持信息搜索能力，并定义搜索 provider、权限、失败体验和引用边界。
- Web Search 触发后默认都进入异步任务，不走同步搜索链路。
- Web Search 等高耗时任务必须采用先确认、后台执行、完成后补发的异步体验。
- 用户明确触发的任务结果补发属于“请求结果投递”，不等同于无触发主动推送。
- 仍必须有任务状态、幂等、发送记录和失败补发。
- 模型不得承诺尚未接入的工具动作。

## 4. 搜索 Provider

Phase 1 默认支持三类搜索 provider：

- DuckDuckGo。
- Tavily。
- Kimi 搜索。

Provider 策略：

- 默认使用 DuckDuckGo。
- DuckDuckGo 不可用、超时、结果质量明显不足或被策略判定失败时，回退到 Tavily 或 Kimi 搜索。
- Tavily 和 Kimi 搜索的具体启用顺序、key、额度、地域和调用配置由内部研发或运营人员在后台配置。
- 用户侧不暴露 provider 选择过程，除非失败体验需要解释“暂时查不了”。
- 所有 provider 调用都必须记录任务、账号、provider、耗时、状态和失败原因，便于成本核算和排查。

## 5. 搜索成本与权益扣减

搜索成本在技术侧按各步骤消耗拆解并累加，再折算成贝壳扣减。

成本组成包括但不限于：

- 搜索意图识别、查询改写和任务规划产生的 LLM token 成本。
- 搜索 provider API 调用成本。
- 搜索结果获取、清洗、去重、排序和摘要处理成本。
- 最终答案生成产生的 LLM token 成本。
- provider 失败后的重试、回退调用和额外摘要成本。
- 异步任务状态、补发消息和 outbound ledger 相关的发送成本。

产品规则：

- 搜索任务必须生成可追踪的成本明细或成本事件。
- 贝壳的具体换算规则放到权益/计费技术或产品文档中定义。
- 搜索失败时是否扣减、扣减多少，需要根据实际已消耗成本和运营策略确定。
- Phase 1 至少要能区分“未实际调用 provider”和“已产生外部/模型成本后失败”。

## 6. 搜索结果要求

- 搜索结果应给出明确来源边界。
- 不确定信息应说明不确定性。
- 不应编造来源、时间或事实。
- 对新闻类结果应优先考虑时效性和来源质量。
- 对高风险领域仍遵守医疗、法律、金融等边界。

## 7. 失败体验

- 默认 DuckDuckGo 不可用时，系统应自动尝试 Tavily 或 Kimi 搜索。
- 所有可用 provider 均失败或不可用：告知暂时查不了，可请用户稍后再试。
- 搜索结果不足：说明没有找到可靠信息，并可建议换关键词。
- 任务超时：补发简短失败说明，不让用户一直等待。

## 8. 验收标准

- Web Search 触发后用户能先收到确认回复。
- 搜索场景默认进入异步任务，不产生同步搜索回复。
- 任务完成后用户能收到完整结果。
- 失败或超时时用户能收到失败说明。
- 任务补发写入 outbound ledger。
- 同一任务不会重复补发。
- 默认搜索 provider 为 DuckDuckGo，失败时能回退到 Tavily 或 Kimi 搜索。
- 搜索任务能记录 provider、状态、耗时和失败原因。
- 搜索任务能生成可追踪的成本明细或成本事件，并可映射到贝壳扣减。

## 9. 待确认

- 搜索引用格式。
- Tavily 与 Kimi 搜索的具体回退优先级和启用条件。
- 搜索失败场景的权益扣减细则。
