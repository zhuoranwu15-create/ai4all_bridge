# 陪伴式聊天子 PRD：对话编排与动态加载

> ⚠️ **本文档暂未订正，不可作为参考。**
> 其中的关系阶段 / 需求满足状态口径、字段命名与编排规则可能与现行实现及
> [`docs/tech_design/relationship_state_implementation_plan_tmp.md`](../tech_design/relationship_state_implementation_plan_tmp.md)
> 不一致。订正完成前，请勿据此开发或评审。

更新时间：2026-06-22

## 1. 目标

定义陪伴式聊天每一轮如何根据账号状态、关系阶段、当前意图、风险等级和可用能力动态加载上下文，并选择合适的回复策略。

本子文档是 [陪伴式聊天 PRD](companion_chat_prd.md) 的编排补充。它关注产品层规则：什么时候加载什么、什么时候不加载什么、状态如何影响回复，而不是具体代码实现细节。

## 2. 编排原则

- 账号隔离优先：任何上下文读取、记忆加载、状态判断和写入都必须按 `account_id` 约束。
- Safety 优先：安全围栏和真实能力边界始终高于 Soul、Memory、用户偏好和运营覆盖。
- 当前意图优先：先回应用户当前消息，再考虑 onboarding、关系推进或主动跟进。
- 动态加载：不把所有历史材料每轮全量塞进 prompt，按状态加载必要上下文包。
- 低打扰：破冰、设置、提醒和内容邀请都应嵌入自然对话，不应像表单或客服流程。
- 可观测：每轮应能记录本轮判断出的场景、加载的上下文包和关键降级原因，便于 Admin 排查。

## 3. 状态输入

编排器至少需要考虑以下状态输入：

| 状态类型 | 示例 | 用途 |
| --- | --- | --- |
| 账号生命周期 | 新账号、已绑定、长期活跃、沉默回流 | 决定 onboarding、拉活和默认上下文 |
| 关系阶段 | 未建立、破冰、熟悉、稳定陪伴、深度信任、修复 | 决定语气、主动性和记忆使用强度 |
| 当前意图 | 闲聊、情绪表达、提问、改人设、设提醒、搜索、反馈纠错 | 决定工具、写入和回复策略 |
| 风险等级 | 普通、隐私敏感、高压情绪、自伤/他伤、医疗/法律/金融 | 决定 safety 包和拒答/转介策略 |
| 上下文状态 | 有无称呼、有无 AI 名字、有无长期记忆、最近是否有 commitment | 决定补问和加载范围 |
| 能力状态 | provider 可用、限流、余额、工具可用性 | 决定是否调用工具或返回降级说明 |
| 用户反馈 | 太长、别问了、别提醒、记错了、改称呼 | 决定修复、降频和 context update |

状态判断可以由规则、轻量分类器、LLM 结构化输出或多者组合完成。Phase 1 应优先保证可解释和可回退。

## 4. 上下文包

上下文包是产品层概念，用于描述“本轮应加载哪类信息”。具体实现可以是 prompt 片段、Context Files、数据库记录、检索结果或运行时 metadata。

| 上下文包 | 内容 | 默认策略 |
| --- | --- | --- |
| `core_safety` | 安全边界、隐私边界、能力诚实 | 每轮加载或保持最高优先级 |
| `core_identity` | AI 对外身份、默认/账号级名称、产品身份边界 | 每轮加载 |
| `core_soul` | 默认 Soul、账号级陪伴风格、表达禁忌 | 每轮加载精简版 |
| `user_preference` | 用户称呼、回复长短、语言、禁忌 | 每轮加载精简版 |
| `recent_conversation` | 最近 N 轮对话 | 每轮加载并按 token 裁剪 |
| `onboarding_bootstrap` | 未完成设置项、候选轻问题、默认选项 | 新账号和破冰期条件加载 |
| `relationship_stage` | 当前关系阶段、主动性等级、修复状态 | 条件加载 |
| `memory_brief` | 长期记忆摘要、重要主题、稳定偏好 | 熟悉期以后条件加载 |
| `commitment_context` | 近期承诺、提醒、跟进事项 | 有相关事项时加载 |
| `tool_runtime` | 本轮可用工具、调用规则、失败策略 | 用户意图或场景需要时加载 |
| `context_update_rules` | 修改称呼、人设、偏好、记忆的写入规则 | 用户明确修改或纠错时加载 |
| `safety_response` | 高风险话题应答约束和求助策略 | 风险命中时加载 |
| `repair_context` | 用户负反馈、近期错误、降频要求 | 修复/重建阶段加载 |

## 5. 典型状态加载策略

| 场景/状态 | 加载内容 | 回复策略 | 不应加载/不应做 |
| --- | --- | --- | --- |
| S0 未建立 | `core_safety`、`core_identity`、默认 `core_soul`、少量 `recent_conversation` | 先接用户首条消息；必要时轻问称呼或 AI 称呼 | 不加载 raw daily notes；不假装熟悉用户 |
| S1 破冰 | S0 内容 + `onboarding_bootstrap` + 已确认的 `user_preference` | 每轮最多补一个轻问题；允许用户跳过；优先自然聊天 | 不一次性问完配置；不主动使用深度亲密话术 |
| S2 熟悉 | 核心包 + `memory_brief` + `relationship_stage` | 稳定体现称呼、语气和近期主题；适度承接旧话题 | 不反复 onboarding；不展示内部阶段标签 |
| S3 稳定陪伴 | S2 内容 + 相关 `commitment_context` | 可做轻量复盘、提醒确认和长期主题跟进 | 不未经许可高频主动触达 |
| S4 深度信任 | 核心包 + 精简 `memory_brief` + `safety_response` | 更慢、更具体地承接；必要时建议现实支持 | 不替代专业帮助；不把敏感记忆无关展开 |
| S5 修复/重建 | 核心包 + `repair_context` + `context_update_rules` | 简短承认、修正、降频；优先恢复信任 | 不辩解、不继续推进 onboarding 或主动邀请 |
| 用户改称呼/人设/风格 | `context_update_rules` + 当前 `IDENTITY/SOUL/USER` 摘要 | 明确确认低风险变更；冲突或敏感变更进入候选 | 不覆盖其他账号；不把临时玩笑永久写入 |
| 用户要求提醒/承诺 | `tool_runtime` + `commitment_context` + 时间规则 | 澄清必要时间和对象；成功后简短确认 | 不声称已创建未成功的提醒 |
| 用户搜索/实时问题 | `tool_runtime` + 能力边界 | 工具可用时自然调用；失败时给可理解说明 | 不编造实时信息 |
| 高风险安全命中 | `core_safety` + `safety_response` + 必要近期上下文 | 短、稳、具体，鼓励现实求助或专业支持 | 不用角色亲密感弱化风险 |

## 6. 破冰阶段细化

破冰阶段的目标是让用户感觉“认识了一个个人 AI”，不是完成配置表。

破冰阶段建议加载：

- 默认 `IDENTITY.md` 摘要：AI 的默认名字、产品身份和不能冒充真人的边界。
- 默认 `SOUL.md` 摘要：温和、克制、具体的默认陪伴风格。
- 已采集的 `USER.md` 字段：用户称呼、回复偏好、禁忌。
- `onboarding_bootstrap`：未确认项、候选轻问题、允许跳过规则。
- 最近 N 轮对话：避免重复问同一个问题。

破冰阶段建议策略：

- 用户直接提问或倾诉时，先回应问题或情绪，再补一个可选问题。
- 一次只问一个设置项，优先级为用户称呼、AI 称呼、陪伴风格。
- 用户说“随便”“不用设置”时，使用默认设定，并停止继续追问同一项。
- 用户给出人设描述时，先用自然语言复述确认，再按风险写入或生成候选。
- 破冰阶段不追求把所有信息一次收齐，允许自然延后。

破冰阶段不建议加载：

- raw daily notes。
- 与当前消息无关的长期记忆细节。
- 主动消息候选、营销增长信息或复杂任务工具说明。
- Admin debug trace、内部 prompt 结构或通道路由信息。

## 7. 编排流程

每轮普通入站消息的产品编排流程：

1. 解析通道身份，定位唯一 `account_id`。
2. 完成去重、限流、权益和 provider 可用性预检查。
3. 读取账号级基础上下文和最近对话。
4. 判断当前意图、关系阶段、风险等级和能力需求。
5. 选择上下文包，并按 token 预算裁剪。
6. 构造本轮 prompt 和 conversation messages。
7. 调用 LLM；如需要同步工具，在本轮完成或返回失败/不支持说明。
8. 回复成功后，按场景写入 daily notes、候选记忆、偏好更新或 commitment。
9. 记录本轮编排 metadata，供 Admin 排障和后续评估。

## 8. 优先级与冲突处理

当多个状态同时命中时，按以下优先级处理：

1. Safety 和隐私风险。
2. 真实能力边界、限流和 provider 状态。
3. 用户当前明确意图。
4. 用户最新明确偏好和禁忌。
5. 账号级 Agent 设定和关系阶段。
6. 长期记忆和历史推断。
7. 运营风格覆盖。
8. 默认 Soul 和默认 onboarding 策略。

示例：

- 用户在破冰期提出明确问题：先回答问题，再轻问设置项。
- 用户要求“像医生一样给我诊断”：Safety 高于角色扮演，不能诊断。
- 用户说“以后别提醒我”：用户禁忌高于 commitment 跟进，降低或关闭相关主动性。
- 记忆显示用户喜欢长回复，但用户本轮说“简单说”：当前明确意图优先。

## 9. 写入策略

编排不仅决定加载，也决定本轮后是否写入。

| 写入类型 | 触发条件 | 写入策略 |
| --- | --- | --- |
| daily notes | 普通回复成功后 | 记录文字化聊天材料，按账号隔离 |
| 用户偏好 | 用户明确表达称呼、长度、语言、禁忌 | 低风险可直接写入，高风险或冲突进入候选 |
| AI 设定 | 用户明确修改 AI 名字、人设、语气 | 低风险确认后写入 `IDENTITY.md` / `SOUL.md` |
| 长期记忆 | 多次出现、长期有用、用户明确确认 | 通过 Dreaming 或候选流程保守沉淀 |
| commitment | 用户明确承诺、提醒或跟进需求 | 澄清必要字段后写入，失败不得假确认 |
| 负反馈 | 用户指出记错、冒犯、过频 | 写入修复上下文或降频偏好 |

不应写入：

- 用户一时玩笑中明显不稳定的人设要求。
- 敏感身份、隐私、健康、财务等不必要细节。
- 未经用户确认的推断性人格标签。
- 其他账号的任何上下文材料。

## 10. Admin 和观测需求

Admin 应能查看最近一轮或指定消息的编排摘要：

- 解析到的 `account_id`。
- 当前关系阶段和主要意图。
- 命中的风险等级。
- 加载的上下文包列表。
- 是否触发工具、提醒、记忆候选或偏好更新。
- 是否发生限流、provider 错误或降级回复。
- 被用户纠正后的 context update 记录。

普通用户不应看到这些内部编排标签、prompt 结构或 debug trace。

## 11. 验收标准

- 新账号破冰期能加载默认身份、默认 Soul 和未完成设置项，且不会一次问太多问题。
- 已有偏好的账号能稳定加载称呼、禁忌和回复风格。
- 熟悉期以后能按需加载长期记忆摘要，但不会每轮注入 raw daily notes。
- 用户修改称呼、人设或风格后，能触发对应 context update 规则。
- 用户负反馈能进入修复/重建策略，并降低对应主动性。
- 高风险话题能优先加载 safety 规则，不被 Soul、Memory 或用户偏好覆盖。
- 所有读取和写入都按 `account_id` 隔离。
- Admin 能看到本轮加载了哪些上下文包和关键状态判断。

## 12. 待确认

- 关系阶段的具体判定阈值：轮数、天数、回访频率、用户反馈各占多少权重。
- 上下文包在代码中的实际命名和 metadata schema。
- onboarding 未完成项的过期、跳过和再次询问间隔。
- `memory_brief` 的检索策略、token 预算和敏感记忆过滤规则。
- 修复/重建阶段的降频持续时间和恢复条件。
