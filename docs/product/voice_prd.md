# 产品专题 PRD：语音输入

更新时间：2026-05-27

## 1. 目标

支持用户在微信私聊中发送语音消息，系统通过豆包 ASR 服务完成转写后进入统一文本对话链路，并返回文本回复。

Phase 1 只支持语音输入，不支持语音回复/TTS。

## 2. 用户流程

1. 用户发送微信语音。
2. OpenClaw / Bridge 将语音 payload 转发到 AI4ALL Backend。
3. Backend 获取语音媒体或可访问引用，并读取语音元数据。
4. Backend 检查语音时长、格式和可访问性。
5. 豆包 ASR 服务转写语音为文本。
6. 转写文本进入普通对话链路。
7. Backend 生成文本回复并通过微信返回。

## 3. 功能需求

- 明确 OpenClaw 语音 payload 结构。
- 保存语音元数据，例如格式、时长、media id、来源引用。
- ASR 服务由豆包提供，并明确失败体验。
- 单条语音最大时长为 60 秒，对齐微信语音时长限制。
- 超过 60 秒的语音不进入 ASR 和 LLM 链路。
- 语音转写后应作为用户消息进入统一会话上下文。
- 语音过长、格式不支持或 ASR 失败时不应继续调用 LLM。

## 4. 体验要求

- 第一版只要求文本回复，不要求语音回复/TTS。
- ASR 失败时提示用户“这条语音我没听清，可以再发一次或打字告诉我”。
- 语音超过 60 秒时提示用户语音太长，可以分段重发或改用文字。
- 语音任务如耗时较长，可先确认收到，再补发回复。

## 5. 风控与成本

- 单条语音最大时长为 60 秒，对齐微信语音时长限制。
- ASR 消耗需要计入贝壳扣减。
- 不应保存不必要的长期语音文件；正式开放前需要明确媒体保留策略。

## 6. 验收标准

- 微信语音输入可以通过豆包 ASR 完成转写。
- 超过 60 秒的语音不会进入 ASR 和 LLM 链路，并有明确失败提示。
- 转写文本能进入统一对话链路。
- 用户收到基于语音内容生成的文本回复。
- ASR 失败有明确失败提示。

## 7. 待确认

- 媒体文件存储与保留策略。
- 是否需要在用户侧展示转写文本。
