# 产品专题 PRD：语音输入

更新时间：2026-06-02

## 1. 目标

支持用户在微信私聊中发送语音消息，并在 `openclaw-weixin` 已提供语音转文字结果时，复用现有文本对话链路返回文本回复。

当前 Phase 1 内测不接入后端豆包 ASR，不下载或转码语音媒体，不做语音回复/TTS。

## 2. 当前产品决策

经真实微信语音链路验证，当前唯一上游 `openclaw-weixin` 会在部分语音消息中提供 `voice_item.text`，并将其映射为入站正文。Bridge 将该正文作为普通 text turn 转发到 AI4ALL Backend。

因此，当前内测口径为：

- 有上游转写文本时，语音按普通文本消息处理。
- Backend 不感知或保存原始语音文件。
- Backend 不调用豆包 ASR，不新增 ASR provider 凭证。
- 不对上游已转写语音单独收取 ASR 贝壳；后续 AI 回复仍按普通聊天扣减。
- 无上游转写文本时，当前不承诺后端 ASR fallback，可提示用户改用文字或重发。

详细证据见 [微信语音输入开发追踪](../tech_design/voice_input_asr_tracking.md)。

## 3. 用户流程

1. 用户发送微信语音。
2. `openclaw-weixin` 处理微信语音，并在可用时产出语音转写正文。
3. OpenClaw before-agent hook 中的 `cleanedBody` 包含转写文本。
4. Bridge 将转写文本作为普通文本消息发送到 Backend。
5. Backend 进入现有文本对话链路。
6. 用户收到文本回复。

## 4. 功能需求

- 支持微信语音在上游已转写时进入普通文本对话链路。
- 转写文本按用户消息保存，并参与上下文、记忆和计费。
- 不保存原始语音文件。
- Admin/Debug 默认按正文类敏感信息处理转写文本。
- 当前不实现后端 ASR、媒体下载、格式校验、60 秒限制和 ASR 成本事件。
- 如 Bridge 收不到可用正文，用户侧应收到可理解的失败或重发提示，不能假装听懂。

## 5. 体验要求

- 第一版只返回文本回复。
- 语音成功转写时，用户体验应与发文字一致。
- 语音未能转写时，提示用户“这条语音我没听清，可以再发一次，或者打字告诉我。”

## 6. 风控与成本

- 不长期保存原始语音媒体。
- 转写文本视为用户聊天正文，遵守隐私与明文访问审计规则。
- 当前不产生 ASR 成本扣减；普通 AI 回复按聊天 token 规则扣减。
- 如果未来接入后端 ASR fallback，再补充语音时长限制、媒体保留、ASR provider 成本和扣费规则。

## 7. 验收标准

- 用户发送微信语音后，如果上游提供转写文本，Backend 能基于该文本生成文本回复。
- Backend `messages` 中保存转写文本，不保存原始语音文件。
- 不出现“语音消息暂不支持”这类错误能力提示，前提是上游已提供转写文本。
- 无上游转写文本时，系统不会进入 LLM 编造语音内容。
- 语音转写文本进入现有上下文和记忆链路，且账号隔离不串线。

## 8. 后续预案

以下内容不进入当前内测首发范围，仅作为未来上游不稳定或新增通道时的 fallback 方案：

- Bridge 提取语音媒体引用。
- Backend 安全下载临时音频。
- 接入豆包或其他 ASR provider。
- 处理 SILK / AMR / WAV 等格式兼容和转码。
- 单条语音时长限制、ASR 失败体验和 ASR 成本扣减。
