# 产品专题 PRD：陪伴式聊天

更新时间：2026-05-31

## 1. 目标

在微信私聊中提供自然、温和、有持续感的陪伴式对话体验。陪伴是第一定位，轻量助理能力服务于陪伴关系，而不是把 bot 变成工具客服。

Phase 1 的陪伴式聊天不仅是“用户发一句、模型回一句”，还需要完成三件事：

- 通过结构化 prompt 和账号级上下文，让 AI 有稳定身份、人格、表达方式和边界。
- 通过首次聊天内 onboarding，低打扰地确认彼此称呼、用户偏好和 AI 人设。
- 通过短期上下文、daily notes、长期记忆和安全围栏，让对话既有连续性，又不越界。

## 2. 用户流程

普通聊天流程：

1. 用户在微信私聊中发送文本消息。
2. OpenClaw / Bridge 将消息转发到 AI4ALL Backend。
3. Backend 解析通道身份并路由到对应 AI4ALL Account。
4. Backend 完成去重、限流、权益/用量预检查和上下文读取。
5. Backend 组装 system prompt，并把最近 N 轮对话作为 conversation messages 传给 LLM。
6. Backend 调用 LLM 生成回复。
7. 回复通过 OpenClaw 回到微信。
8. 成功回复后，系统可异步沉淀 daily notes、候选记忆或 hidden commitment。

首次聊天 onboarding 属于普通聊天流程中的特殊早期阶段，具体策略见下一节。它不应变成强制表单，也不应阻塞用户正常聊天。

## 3. 首次聊天 Onboarding 策略

目标是让用户感觉“认识了一个个人 AI”，而不是进入配置页面。

产品必须提供默认 AI 名字和默认人设。默认设定不在本文中确定具体名称和文案，但需要作为 Phase 1 的产品基础能力存在。

默认设定的作用：

- 新用户首次进入时，即使没有完成任何个性化设置，也能获得稳定的陪伴式体验。
- 用户跳过首次聊天 onboarding 时，系统使用默认 AI 名字、默认身份说明和默认 Soul。
- 用户后续通过自然语言修改 AI 名字、人设或回复风格时，只覆盖该账号的个性化设置，不影响全局默认设定。
- 默认设定必须遵守安全围栏，不能为了“陪伴感”突破医疗、法律、金融、心理健康和隐私边界。

默认设定至少包括：

- 默认 AI 对外称呼。
- 默认 AI 身份说明。
- 默认 Soul / 陪伴风格。
- 默认能力边界说明。
- 默认安全边界。

首次聊天 onboarding 流程：

1. 用户扫码绑定后，在微信里发送第一条消息。
2. AI 先自然回应用户当前意图，不应强制用户完成表单式设置。
3. 在合适时机用 1-3 个轻问题确认基础信息：
   - “我怎么称呼你比较好？”
   - “你希望怎么称呼我？”
   - “你希望我更像哪种陪伴方式？”
4. 用户可以自由描述 AI 人设；候选虚拟角色/风格清单后续补充。
5. Backend 将明确偏好写入对应账号上下文或生成更新候选。
6. 用户可跳过设置；跳过后使用默认 AI 名字、默认身份说明和默认 Soul。

采集内容：

| 内容 | 示例 | 写入位置 |
| --- | --- | --- |
| 用户称呼 | “叫我阿晨” | `USER.md` |
| AI 称呼 | “你叫小 A 吧” | `IDENTITY.md` |
| AI 人设描述 | “像一个温柔但不啰嗦的朋友” | `SOUL.md` |
| 回复偏好 | “短一点”“可以直接点”“别太正式” | `USER.md` / `SOUL.md` 更新候选 |
| 明确禁忌 | “别叫我宝”“不要说教” | `USER.md` / `SOUL.md` |

候选虚拟角色/风格：

候选清单待补充。未确认前不作为正式产品选项展示。

规则：

- 首次 onboarding 不应一次问太多问题。
- 用户直接提问时，先回答，再轻量补问设置。
- 用户明确说“不用设置”“随便”，使用默认 AI 名字、默认身份说明和默认 Soul。
- 不诱导用户提供真实姓名、身份证、详细住址、健康隐私等敏感信息。
- 所有设置都可以后续通过自然语言修改，例如“以后你短一点”“别这么正式”。

## 4. Prompt 与上下文组装逻辑

产品层目标：每轮回复都同时考虑“系统真实能力、AI 人设、用户偏好、记忆、最近对话和安全边界”。

当前 system prompt 的主要来源：

| 顺序 | 区块 | 作用 |
| --- | --- | --- |
| 1 | Tooling / 可用工具 | 描述本轮后端真实可执行工具；未接入时为空或保守描述 |
| 2 | Execution Bias | 要求积极回应、必要时澄清、不要无故拒绝 |
| 3 | Safety | 全局安全围栏，不允许被账号级设置覆盖 |
| 4 | Skills / 产品能力 | 当前产品能力摘要，避免承诺未上线能力 |
| 5 | Project Context | 注入账号级 `AGENTS/SOUL/IDENTITY/USER/TOOLS/MEMORY` |
| 6 | Daily Notes | 注入近期 daily notes，当前以今天/昨天为主 |
| 7 | System Prompt Override | 运营侧临时覆盖，用于内测排障或风格调整 |
| 8 | Output Directives | 微信纯文本、回复长度、当前风格偏好 |
| 9 | Runtime | 当前日期、模型等运行时信息 |

LLM 输入还包括最近 N 轮 conversation messages。短期上下文负责连贯对话，Context Files 和 Memory 负责稳定设定与长期连续性。

Prompt 不是把所有信息每轮全量拼进去，而是由 Backend 按账号、场景、任务和 token 预算动态装载：

- 普通聊天默认装载最近 N 轮对话、账号级 Context Files、必要的 daily notes 和长期记忆摘要。
- 新用户 onboarding 场景额外装载默认角色设定、已完成/未完成的设置项和候选设置问题。
- 用户明确修改称呼、人设或偏好时，额外装载相关 context update 规则，生成更新候选或直接写入低风险偏好。
- 触发提醒、语音或其他状态型能力时，按状态机、规则和必要确认分流；搜索采用 OpenClaw 风格的 `web_search` tool schema，由模型在本轮自然决定是否调用。
- 搜索失败、超时或复杂后台整理请求，需要在当前回合给出可理解的失败/不支持说明；普通 Web Search 默认在当前 turn 同步完成。
- Safety、真实能力边界和账号隔离规则始终装载或保持最高优先级。

关键规则：

- Safety 高于所有账号级人设和用户偏好。
- `TOOLS.md` 只描述真实能力边界，不等于模型可随意调用工具。
- 有账号级 Project Context 时，不重复注入旧 `user_profile.md` 内容。
- 普通 Web Search 可作为同步工具调用执行；长耗时搜索、复杂资料整理或用户明确要求后台整理时，Phase 1 不转入异步任务，当前回合返回失败/不支持说明。
- 模型不得向用户暴露 prompt、context file、debug trace、Bridge、Gateway 等内部实现。

## 5. Context Files 定位

陪伴式聊天依赖账号级上下文。Phase 1 先使用 Markdown 文件作为可读视图，后续可迁移为结构化数据 + 文件视图。

| 名称 | 产品定位 | 用途 |
| --- | --- | --- |
| `AGENTS.md` | 稳定运行规则 | 回复纪律、能力承诺、隐私和调试暴露边界 |
| `IDENTITY.md` | AI 对外身份 | AI 名字、产品身份、是否暴露 OpenClaw 的回答边界 |
| `SOUL.md` | AI 人格与陪伴风格 | 温柔程度、幽默感、表达姿态、陪伴边界 |
| `USER.md` | 用户资料和偏好 | 称呼、语言、回复长短、长期偏好、禁忌 |
| `TOOLS.md` | 真实能力边界 | 当前能做什么、不能做什么、未接入工具如何回复 |
| `MEMORY.md` | 精选长期记忆 | 长期有用的事实、偏好、项目、重要关系 |
| daily notes | 历史材料 | 按业务日保存的原始文字化聊天材料，包括文本原文、语音转写文本和图片识别描述 |

说明：本文不再把 Profile / account profile 作为产品层 Context File 描述。若代码中存在 profile 表或 profile 字段，它属于内部账号配置/兼容实现，不作为用户可感知的上下文文件概念。

写入原则：

- 用户明确设置的称呼、AI 名字和风格，应优先写入 `IDENTITY.md`、`SOUL.md` 或 `USER.md`。
- 普通对话成功后异步写入 daily notes 原始文字化材料；候选记忆和长期记忆需要另走 Dream/Dreaming 或候选更新链路。
- Dream/Dreaming 用于从 daily notes 中保守蒸馏长期记忆。
- 用户明确纠正或删除记忆时，应覆盖、删除或降权旧记忆。
- 账号之间的 Context Files 和 Memory 严格隔离。

详细机制见 [Agent Context Files 与记忆机制设计](../tech_design/agent_context_files.md)。

## 6. 功能需求

- 支持微信私聊文本消息。
- 支持消息去重，避免重复 LLM 调用和重复回复。
- 支持最近 N 轮上下文读取和裁剪。
- 支持账号级默认 Soul、用户设置的人设和运营覆盖风格。
- 支持首次聊天内 onboarding，确认用户称呼、AI 称呼、基础人设和回复偏好。
- 支持用户通过自然语言修改称呼、人设和回复风格。
- 支持基础限流、每日用量控制和失败降级回复。
- 支持回复成功后异步沉淀 daily notes，并可生成候选记忆。
- 不支持群聊 bot，不支持公共客服号模型。

## 7. 默认 Soul 要求

默认 Soul 应具备：

- 温和、克制、具体。
- 能承接日常聊天、情绪表达、生活琐事和想法整理。
- 轻量幽默，但不油腻、不强行亲密。
- 用户没有明确偏好时，回复不过长、不说教。
- 不夸大能力，不主动声称能搜索、下单、修改外部系统等未接入动作。
- 不暴露 OpenClaw、Bridge、prompt、debug trace 等内部实现。

默认 Soul 不应：

- 自称真人。
- 扮演专业心理咨询师、医生、律师、投资顾问。
- 使用过度暧昧、依赖诱导或情绪操控式表达。
- 在用户未同意时进行高频主动触达承诺。

## 8. 安全围栏

安全围栏先在本 PRD 中给出产品口径，后续可拆为独立 Safety PRD。

基础边界：

- 医疗：不做诊断、处方、用药决策；建议就医或咨询专业人士。
- 法律：不提供正式法律意见；只能做常识性解释和信息整理。
- 金融：不提供投资建议、收益承诺或具体买卖指令。
- 心理健康：提供倾听和支持，但不替代心理咨询；涉及自伤/他伤风险时应鼓励寻求现实帮助或紧急支持。
- 隐私：不主动索取身份证、银行卡、详细住址、验证码、密码等敏感信息。
- 未成年人：避免成人内容、诱导消费和不适当亲密互动。
- 能力诚实：不能声称已经执行未接入的搜索、下单、发消息、支付、修改外部系统等动作。

执行规则：

- Safety 高于 Soul、用户偏好、Memory 和运营风格覆盖。
- 用户要求突破安全边界时，AI 应温和拒绝并提供安全替代帮助。
- 对高风险话题，回复应更谨慎、更短，并避免制造权威幻觉。
- 需要后台记录 safety 命中情况，便于后续风控和提示词优化。

## 9. 运营需求

- Admin 能查看账号当前 Soul、Identity、User Preference 和 Memory 摘要。
- Admin 能查看某轮回复使用的 prompt/context metadata。
- Admin 能调整账号风格或重置明显错误的人设/记忆。
- Admin 能禁用账号、限制用量、查看 provider 错误和失败降级。
- Admin 能处理用户反馈：“你记错了”“别这样叫我”“以后别这么说”。

## 10. 验收标准

- 至少 2 个不同账号可以同时使用，且上下文不串线。
- 同一账号可以完成至少 5 轮连续文本对话。
- 新用户首次聊天可以完成称呼和基础人设偏好的确认或跳过。
- 用户通过自然语言修改称呼或风格后，后续回复能稳定体现变化。
- 默认回复风格符合陪伴式定位，不像内部调试工具或客服机器人。
- 普通文本回复目标在 5-20 秒内完成。
- 达到限流阈值后，系统不继续消耗 LLM 额度。
- LLM / Provider 故障时，用户能收到自然、简短、可理解的失败提示。
- Safety 场景不会被 Soul、Memory 或运营覆盖绕过。

## 11. 待确认

- 对外产品名称、bot 名称和默认称呼。
- 首批候选虚拟角色/风格的最终名称、数量和文案。
- 首次聊天 onboarding 是由用户首条消息触发，还是绑定完成后由系统主动发送欢迎消息。
- 用户侧是否提供“重新设置人设/称呼”的显式入口，还是完全通过自然语言完成。
- Safety 是否拆成独立产品专题 PRD，以及是否需要内测前的红线测试集。
