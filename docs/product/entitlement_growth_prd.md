# 产品专题 PRD：贝壳、增长与支付后置

更新时间：2026-06-02

## 1. 目标

支撑 Phase 1 正式内测发布所需的产品内权益额度、用量扣减、拉新奖励和基础客服处理。支付和用户购买正式后置，不进入 Phase 1 内测首发范围。

权益额度暂定命名为“贝壳”。贝壳是产品内额度，不是链上资产，不可提现，不对外承诺金融属性。命名含义来自贝壳作为早期人类货币的具象象征。

## 2. 产品定义

贝壳数量表示用户在 AI4ALL 业务系统内可消耗的权益额度。

用途：

- 记录新用户注册赠送额度。
- 记录运营发放、补偿发放、活动发放。
- 记录拉新奖励。
- 记录未来购买额度（支付后置，当前不开放）。
- 抵扣 LLM、搜索等用户使用服务产生的资源消耗。

默认赠送：

- 新用户注册成功后，默认赠送 1000 个贝壳。
- 拉新成功后，暂定给邀请人赠送 1000 个贝壳。

## 3. 计价与扣减

### 3.1 基础换算

Phase 1 默认以 `deepseek v4-flash` 作为基准模型。

基础换算规则：

- 1000 个 `deepseek v4-flash` token 消耗 1 个贝壳。
- 聊天默认按输入 token 和输出 token 加和计算消耗。
- 如果一次聊天消耗 `input_tokens + output_tokens = 2500`，则按基准模型计算为 2.5 个贝壳。

### 3.2 不同模型价格倍率

如果后续接入单价更贵或更便宜的模型，需要按该模型相对 `deepseek v4-flash` 的价格倍率折算贝壳消耗。

示例：

- 某模型单价是 `deepseek v4-flash` 的 1.5 倍。
- 则 1000 个该模型 token 消耗 1.5 个贝壳。
- 同理，2000 个该模型 token 消耗 3 个贝壳。

产品原则：

- 模型价格倍率由后台配置，不暴露给普通用户。
- 每笔扣减流水需要记录模型、输入 token、输出 token、价格倍率、折算后的贝壳消耗和业务来源。
- 是否做小数贝壳展示、最小扣减粒度和四舍五入规则，后续在技术/计费细则中确定。

### 3.3 搜索等工具/任务消耗

搜索默认走同步 `web_search` 工具调用；长耗时搜索、复杂整理或后台报告请求在 Phase 1 当前回合返回失败/不支持说明，不转为异步任务。

Phase 1 暂定扣减规则：

- 每次成功触发商业搜索 provider 的 `web_search`，固定扣减 5 个贝壳。
- 5 个贝壳用于覆盖约 3 分钱人民币的外部搜索 API 成本和少量结果处理成本。
- 搜索所在 turn 的 LLM 工具决策、最终回答 token 仍按普通聊天规则另行扣减。
- 未实际调用商业 provider 的失败搜索不扣这 5 个贝壳；已调用 provider 但后续回答失败的场景，先记录成本事件，后续通过客服/运营补偿处理。

成本明细仍需要可追踪，原则上记录以下信息：

- 当前 LLM turn 的工具决策、最终回答 token 成本。
- 可选查询改写和结果整理的 token 成本。
- 搜索 provider API 调用成本。
- 搜索结果处理、摘要和最终生成的 token 成本。
- provider 失败后的重试、回退和额外处理成本。

Phase 1 产品文档明确：搜索等工具调用必须生成可追踪的成本明细或成本事件；商业搜索 provider 成功调用后按 5 贝壳扣减。后台整理、长耗时报告和异步补发不进入 Phase 1。

### 3.4 主动触达消耗

主动触达类首条消息不扣用户贝壳，包括用户提醒到期投递、陪伴跟进首条消息和内容推送首条消息。

用户收到主动触达后，如果继续回复并进入普通聊天或搜索链路，则从用户回复后的 AI 回复或同步搜索开始，按对应聊天或搜索规则扣减贝壳。

说明：

- 首条主动触达仍需要记录发送成本、模型成本和 outbound ledger，但该成本默认计入平台运营成本，不从用户贝壳余额扣减。
- 用户显式触发的搜索等工具调用，执行本身仍按搜索成本规则扣减；Phase 1 不支持用户请求后的异步任务结果补发。
- 用户提醒的到期投递是用户已设置任务的执行结果，投递本身不扣贝壳；如果提醒后用户继续聊天，后续聊天按普通聊天规则扣减。

## 4. 功能需求

- 支持内测版贝壳赠送规则配置。
- 支持产品内贝壳账户。
- 支持注册赠送、拉新赠送、运营手工发放、补偿发放和活动发放。
- 支持按 LLM token、搜索等资源消耗扣减贝壳。
- 支持记录主动触达首条消息的平台成本事件，但默认不从用户贝壳余额扣减。
- 每笔发放、扣减、补偿都必须有可审计流水。
- 支持邀请关系记录和拉新奖励规则。
- 支持客服/运营处理额度补发、误扣排查和绑定异常。

## 5. 拉新激励

拉新奖励暂定为 1000 个贝壳。

拉新流程：

1. 老用户分享自己的邀请码，或分享带自己邀请码的注册网站链接。
2. 新用户打开带邀请码的链接时，注册页自动填充老用户的邀请码。
3. 如果新用户不是通过邀请链接进入，也可以在注册页手动输入邀请码。
4. 新用户完成注册和绑定。
5. 新用户发送 3 条有意义信息。
6. 后台 AI 判断这 3 条信息是否为有意义信息。
7. 判定通过后，系统记录拉新成功，并发放拉新贝壳奖励。

产品规则：

- 拉新奖励暂定发放给邀请人 1000 个贝壳。
- 新用户自己的注册赠送仍按默认规则获得 1000 个贝壳。
- 邀请码需要绑定邀请人账号，并记录新用户注册、绑定、消息达标和奖励发放状态。
- 如果 AI 判断 3 条信息不具备真实意义，不计为拉新成功。
- 需要预留反作弊策略，例如重复手机号、重复设备、异常批量注册、无意义消息刷量。

## 6. 支付后置

Phase 1 内测首发正式不开放支付和用户购买，不实现：

- 创建订单。
- 支付回调。
- 支付状态查询。
- 贝壳生效。
- 退款/异常处理。
- 对应审计流水。

内测通过注册赠送、运营补发、活动发放和拉新奖励运行。

后续如开放购买，价格锚点暂定：

```text
1 元人民币 = 100 个贝壳
```

支付 provider、套餐结构、退款策略和支付合规边界后续单独立项。

## 7. 用户与客服可见性

- 用户或客服至少能确认剩余贝壳数量。
- 用户或客服至少能确认发放记录和消耗概况。
- 客服能补发贝壳、记录处理原因、排查误扣。
- 面向用户的文案应使用“贝壳”，避免暴露底层 token、模型倍率和 provider 成本细节。

## 8. 验收标准

- 新用户注册成功后可以获得 1000 个贝壳，且贝壳能生效到账号。
- 默认聊天消耗能按输入 token + 输出 token 计算，并按 `1000 deepseek v4-flash token = 1 贝壳` 生成扣减流水。
- 模型价格倍率能影响贝壳扣减，例如 1.5 倍单价模型的 1000 token 消耗 1.5 个贝壳。
- LLM / 搜索等消耗能生成贝壳扣减流水。
- 每次成功触发商业搜索 provider 的 `web_search` 暂定扣减 5 个贝壳。
- 主动触达首条消息不扣用户贝壳，但能记录平台成本事件；用户回复后的后续 AI 回复或任务执行按对应规则扣减。
- 老用户可分享邀请码或带邀请码注册链接，新用户注册页能自动填充或手动输入邀请码。
- 新用户完成注册绑定并发送 3 条有意义信息后，系统能判定拉新成功并给邀请人发放 1000 个贝壳。
- 管理者可以补发贝壳、查看邀请关系、排查误扣并记录基础客服处理。
- 支付/购买不作为 Phase 1 内测验收项；后续如开放购买，价格锚点暂定 `1 元人民币 = 100 贝壳`。

## 9. 待确认

- 贝壳是否为最终正式名称。
- 小数贝壳展示、最小扣减粒度和四舍五入规则。
- 搜索失败、provider 已计费但最终回答失败等边界场景的补偿口径。
- 主动触达首条消息的平台成本记录口径。
- 拉新奖励是否也给被邀请人额外奖励。
- 后台 AI 判断“有意义信息”的标准、阈值和人工复核机制。
- 反作弊策略的具体实现。
- 支付后续立项时的 Provider、套餐结构、退款策略和合规边界。
- 业务逻辑放在本仓库还是拆成 billing/growth/support 服务。
