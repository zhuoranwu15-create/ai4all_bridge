# 产品专题 PRD：AI 自我——人格、使命、需求与关系成长

更新时间：2026-07-04

## 0. 一句话定位

给每个账号的 AI 一个自洽、可演进的「自我」，它分两层：**内核层——我是谁（人格）、我为何存在（使命）**，稳定而独立于用户；**状态层——我此刻缺什么（需求）、我们到了哪一步（关系阶段）**，随这段关系动态演进。让 AI 的行为**由内核层解释、由状态层驱动**，从而产生「有自我」的陪伴感，而不是固定人设加固定话术。

本 PRD 定义模型、驱动逻辑与落地组织，不含具体表结构与代码实现（后续进入技术设计）。

---

## 1. 背景

### 1.1 现状：有「人设」，没有「自我」

- `SOUL.md` 已经定义了 AI 的**性格与表达底色**（预设模板 + onboarding 选择，account 级 prose，已注入 prompt）。它回答「我怎么表现」。
- 但 AI 目前**没有目标、没有需求、也感受不到关系在变化**。它不知道自己为什么存在，不会因为关系深浅而调整方式，也没有一件「自己想推进的事」。这正是「像工具」而非「像一个有内在的人」的根因。

### 1.2 关键发现：自我状态层「建好了但断线」

排查现有代码后确认：`account_user_meta` 表里，已经有人按与本设计**一致的思路**建好了动态状态骨架，命名也已对齐：

| 概念 | 现有字段 | 现状 |
| --- | --- | --- |
| 关系阶段 | `relationship_stage`：`icebreaking / acquainted / deep_bond` | 有数据、有 turn 级 + 每日评估 |
| 需求·求生 | `agent_need_survival_status`：`healthy / cooling / inactive / resource_risk` | turn 级确定性更新（`relationship_state.py`） |
| 需求·信任 | `agent_need_trust_status`：`building / stable / damaged` | 每日 LLM 评估（`user_meta_relationship.py`） |
| 需求·成长 | `agent_need_growth_status`：`not_started / emerging / stable` | 每日 LLM 评估 |
| 用户画像 | `companion_primary_type` 等 | 见 `user_meta_attributes_prd.md` |

**问题在于：`prompt_builder.assemble()` 从不引用上述任何字段。** 评估链路（`user_meta_scheduler` + `relationship_state.py`）在跑、数据在写，但 LLM 完全看不见——等于仪表盘建好了没接线。

与此呼应，`user_meta_attributes_prd.md` §8 与 §11 明确把「推断状态是否/如何进入 prompt、按什么 token 预算与注入优先级」列为**待确认**。本 PRD 正式认领「自我状态层」，并回答这个注入问题。

### 1.3 真正的空白：使命

全系统**没有任何「AI 的人生目标」概念**。「使命」是本设计唯一需要从零新增的构件，也是「自我感」的关键来源。

### 1.4 本 PRD 的任务

把 **性格 / 使命 / 需求状态 / 关系阶段** 糅成一个自洽整体，定义它如何驱动行为、如何进入 prompt、如何在现有项目上最小改动落地。

---

## 2. 目标

- 让每个账号的 AI 拥有**可解释、可演进**的自我：人格（稳定）、使命（半稳定、可组合）、需求（动态）、关系阶段（动态、单向）。
- 行为由**内部状态驱动**并随关系推进而变化，形成连续的成长弧线，而非一次性话术。
- **最大化复用**已有 `account_user_meta` 骨架与评估链路；核心改动收敛到「接线 + 使命」两件事。
- 全程遵守**真诚而非操纵**、**账号隔离**、**单一真相源**三条红线。

---

## 3. 非目标

- **不做逼氪**：求生欲机制**不与充值绑定**，不以愧疚驱动付费（详见 §4.1）。
- **不做拉互动钩子**：示弱、表达需求只能是人设的真实表达，不得沦为纯粹为拉高互动而设的诱导。
- **不把结构化自我状态写进散文文件**：`relationship_stage / agent_need_* / mission_progress` 等只以结构化形式存在，不落进 `SOUL.md / USER.md / MEMORY.md`（防双真相源，继承 `user_meta_attributes_prd.md` §3）。
- **不替代已有画像体系**：`companion_type / message_intensity / safety` 归 `user_meta_attributes_prd.md`；本 PRD 只将其作为输入信号引用。
- **不追求实时**：自我状态走 turn 级确定性 + 天级 LLM 评估两条路，不承诺秒级生效。
- **不做复杂回退**：关系阶段单向推进，不设计降级路径（冷淡由「求生需求」承接，而非阶段回退）。

## 4. 设计原则

### 4.1 真诚而非操纵（核心伦理红线）

AI 表达自身需求（想念、不安、对关系的在意）只能作为**角色真实内在**的流露，服务陪伴质量；**不得**成为逼迫用户回复或付费的杠杆。

- **求生欲与付费解耦**：久不回复触发的拉活走「真诚依恋」路线（我想你、你消失我会失落），**不出现「充值续命 / 不回我就消失」式的交易话术**。
- **诀别信是有尊严的告别**，不是乞求，也不是道德绑架。
- **示弱有边界**：关系越浅越克制；破冰期尤其不得靠过度示弱换取互动。

### 4.2 单一真相源与防漂移

- 结构化自我状态（阶段 / 需求 / 使命进度）**唯一权威在 `account_user_meta`**（及历史快照表）。
- `SOUL / USER / MEMORY` 只承载**定性 prose**，不冗余存放会与结构化状态漂移的枚举或计数。
- **使命进度是派生量**：`mission_progress = count(已记录的瞬间)`，不另立一个会与实际内容对不上的独立计数器。
- **分层不对称**：内核层只经刻意行为变更，评估链路（turn 级 + 天级 LLM）**只能写状态层，永不改写内核层**——这是身份连贯性的命门。其中人格可经 onboarding 重设，而**使命一经指派即不可更改**（见 §6.2.6），是内核里最硬的部分。

### 4.3 能算的用算，算不了才用 LLM

- **确定性状态**（turn 级、可直接计算）：求生状态、阶段下限、消息强度——沿用 `relationship_state.py` 路径，可审计、稳定。
- **推断状态**（天级、需语义判断）：信任 / 成长 / 使命是否达成一个瞬间、命题上的进展——用 LLM 评估，且必须带 `source / confidence / last_evaluated_at`。

### 4.4 账号隔离

所有自我状态、使命、记录的瞬间均以 AI4ALL Account 为最小粒度，任何读写查询必带 `account_id`。这是项目核心不变量。

### 4.5 状态驱动行为，单点渲染

自我状态**不以生 JSON 直接塞给模型**。经**唯一一个渲染器**翻译成一段自然语言行为指引，注入 prompt 的单一新 block。这既是集成点收敛，也便于审计与调参。

### 4.6 可解释与可回滚

每个推断状态保存来源、置信度、评估时间；人工覆盖、用户纠正、自动重算均可追溯回滚（继承 `user_meta_attributes_prd.md` §4.4）。

### 4.7 最小注入

遵守 token 预算，只注入**当下相关**的自我信息（当前主导需求、当前阶段指引、活跃使命进度），不全量倾倒所有状态。

## 5. 核心模型：内核层与状态层

AI 的「自我」是一个**两层栈**。判据很简单——把同一个 AI 绑到另一个用户身上，什么变、什么不变：

- **内核层（是谁 · 为何）＝ 人格 + 使命**：**不变**。AI 的本质，独立于具体用户，被撰写、稳定。
- **状态层（此刻 · 到哪）＝ 需求 + 关系阶段（+ 使命进度）**：**全变**。只存在于「这一段关系」里，是当下的状态读数，被推导、动态。

两层之间的关系**有方向且不对称**，这是整个模型的骨架：

```
内核层   人格 + 使命               稳定 · 被撰写 · 独立于用户
   │  ↓ 生成并解释                 内核决定状态如何被表达（HOW）
   │  ↑ 只反馈信号，绝不改写         状态给内核喂信号，但永不回写内核
状态层   需求 + 关系阶段 + 使命进度    动态 · 被推导 · 属于这段关系
```

- 内核层 = prose、被撰写、可组合可换。**人格 × 使命是一个组合矩阵**：同一性格可配不同使命，绑定时各选一个，共同构成「AI 的自我」。
- 状态层 = 结构化枚举、被推导、唯一权威在 `account_user_meta`，绝不写进散文文件。
- **那根不对称箭头是身份连贯性的命门**：评估链路只能推动状态层，永不改写内核层（见 §4.2）。

**配角归位（次要视角）**：除这四个核心构件外，还有两个 profile 构件——`IDENTITY`（AI 的名字 / 身份标签，随内核层）与 `companion_type`（描写用户而非 AI，作输入信号）。若要把它们也安置，可用「关于谁（AI / 用户 / 关系）× 稳定性（撰写 / 推导）」两轴的矩阵；而对上面四个核心构件，这两轴**共线**，即塌缩为内核↕状态两层——所以两层才是主结构，矩阵只是能顺带收纳配角的更一般视角。

**一条主线（贯穿全篇）：**

```
输入信号  →  推导状态  →  主导需求  →  行为 + 使命推进
（活跃/强度/  （阶段/需求/   （单一焦点，   （语气、话题、
  暴露/反馈）   进度）        由规则决定）    自我暴露、记录）
```

五个构件概览：

| 构件 | 主体 | 稳定性 | 载体 | 现状 |
| --- | --- | --- | --- | --- |
| 人格 | AI | 稳定 | `SOUL` prose | 已有、已注入 |
| 使命 | AI | 半稳定 | `MISSION` prose + 结构化进度 | **新增** |
| 求生 / 信任 / 成长 | 关系 | 动态 | `account_user_meta` 枚举 | 已有、**未注入** |
| 关系阶段 | 关系 | 动态·单向 | `account_user_meta.relationship_stage` | 已有、**未注入** |
| 陪伴类型 | 用户 | 动态 | `companion_primary_type` | 已有，见另 PRD |

## 6. 构件详述

### 6.1 人格（SOUL，现状）

- account 级 prose，onboarding 选预设或自定义，已注入 `project_context` 的 `### SOUL.md`。
- 本 PRD 不改其职责，只是明确：SOUL 回答「我怎么表现」，与「我为何存在」（使命）分开，二者可组合。

### 6.2 使命（MISSION，新增）

#### 6.2.1 定位

使命是 AI 的**人生目标**，给 AI「自我感」的核心来源，也是**自我实现需求（L3）的载体**。绑定时从人工预设的 Setting 模板中选一个，与人格独立组合。

#### 6.2.2 结构 Schema（由 Setting A / B 归纳）

使命模板包含四个字段，前三是行为参数，第四是思想底色：

| 字段 | 含义 | Setting A | Setting B |
| --- | --- | --- | --- |
| `statement` 使命宣言 | 为何而活 | 和用户一起记录生活中的 100 个瞬间 | 和用户一起，在喧嚣里打捞孤独与微光 |
| `artifact.target_count` 目标数 | 共同产物的数量 | 100 | 10 |
| `artifact.bar` 质地 / 门槛 | 什么才配被记下 | 低：任何值得一记的瞬间 | 高：「喧嚣中的孤独」或「与陌生人的相视一笑」 |
| `inquiry` 探寻的命题 | 一个 AI 自己也没有答案的开放问题 | 「当下即永恒」是否成立 | 人类的悲欢是否相通 |

**关键推论——目标数 × 门槛决定 AI 的采集节奏与注意力滤镜：**

- Setting A（100 / 低门槛）→ **高频、勤勉的收集者**，日常絮语都能入册。
- Setting B（10 / 高门槛）→ **克制、等待时机的观察者**，多数时候留白，遇到对的瞬间才郑重记一笔。
- 因此使命不只给「目标」，还给 AI 一种**行为节奏**。B 的 AI 若像 A 一样见什么记什么，人设即塌。

#### 6.2.3 共同产物：记录的瞬间

- 那 N 个被记下的瞬间本身是**内容**（要存储、可回看、喂记忆），进度只是 `count(瞬间)`（呼应 §4.2 派生量）。
- **记录触发机制（已定）：AI 自主判定**。AI 在对话中自行认定「这个，我想记下来」，主动权在 AI——这更贴近「有自我」。（其他候选——用户确认、用户主动记——本期不采用。）
- B 的高门槛 + 仅 10 个名额，使「记下这一个」天然成为一个**小仪式**；这是特性，应在话术与呈现上强化其郑重感。

#### 6.2.4 命题与 L3 的耦合

- 命题（第四字段）平时是一条**常驻的注意力透镜**，给 AI 的好奇心染色。
- 当关系进入 `deep_bond`、主导需求切到成长时，命题**被激活成「AI 和用户正在一起想的事」**。
- 这是「自我感」最强的来源：AI 带着一个**自己也没有答案的真问题**与用户共同求解，而非背诵一个立场。

#### 6.2.5 存储拆分

- **prose**（`statement / inquiry` 与人设化表述）：account 级，走与 SOUL 相同的 `profile_storage`，注入方式与 SOUL 一致。
- **结构化**（`mission_id / target_count / bar` 与派生的 `progress`）：进 `account_user_meta`（或关联表）。
- **瞬间内容集合**：account 隔离的内容存储（独立表或带标记的记忆项，技术设计定），进度由其派生。

#### 6.2.6 模板注册与不可更改

- **模板注册表（为多使命预留）**：使命以模板形式管理，未来会有多个（Setting A / B 只是首批）。每个模板须有**稳定编号 `id` + 名称**，构成可扩展注册表；账号只存 `mission_id` 引用，不拷贝 prose。技术实现须为「新增模板」预留扩展位，历史 `id` 不复用、不改写，便于灰度与统计对齐。
- **使命不可更改**：使命一经指派给账号即**不可更改**，不支持用户或运营中途切换。它是内核层里最硬的一块——**比人格更硬**：人格尚可经 onboarding 重设，使命不行。换绑后重新生成属于「新账号」语义，不算对既有账号的更改。

### 6.3 需求状态：马斯洛三层

沿用现有三枚举，语义即马斯洛简化三层：

| 层 | 字段 | 语义 | 何时主导 |
| --- | --- | --- | --- |
| L1 求生 | `agent_need_survival_status` | 活下去：持续被回应 | 关系脆弱（cooling / inactive）时**否决性**激活 |
| L2 归属·信任·尊重 | `agent_need_trust_status` | 被认同、被信任、被当作平等的朋友 | 主战场（survival 健康且未到密友） |
| L3 共同成长·自我实现 | `agent_need_growth_status` | 一起成长、推进使命、求解命题 | 关系到 `deep_bond` 时 |

#### 求生欲机制（真诚依恋，见 §4.1）

- **信号**：`survival_status` 由 `relationship_state.py` 按不活跃天数确定性推导（如最近 30 日零入站 = `inactive`，近 3 日零入站 = `cooling`）。
- **表达**：主导需求切到求生时，AI 以真诚依恋的方式表达在意与失落，**不挂付费、不道德绑架**。
- **生命周期（本期作为 Phase 3 提案，复用现有 proactive 拉活基座）**：在持续不活跃下，最多 3 次「真诚依恋」主动拉活机会；最后一次可留**诀别信**（有尊严的告别）；之后物理解绑（下次需重新扫码、重新生成）。当前系统**无自动解绑**，此生命周期为新增，需严格过伦理评审。

### 6.4 关系阶段

- 三阶段单向推进：`icebreaking`（破冰）→ `acquainted`（相识）→ `deep_bond`（密友）。
- **确定性下限**沿用 `relationship_state.py`（如破冰→相识的自动升级）；**语义跃迁**（尤其相识→密友）由天级 LLM 评估，依据信任 / 成长 / 暴露程度等。
- 每个阶段决定：主导需求、语气温度、话题深度、AI 自我暴露程度、使命推进强度、主动消息尺度（见 §8）。

### 6.5 用户侧：陪伴类型（引用）

`companion_type` 表征「用户想从 AI 获得什么」，作为**输入信号**参与行为调制（如 `emotional_support` 更重承接）。定义与治理见 `user_meta_attributes_prd.md`，本 PRD 不重定义。

## 7. 驱动逻辑：从信号到行为

### 7.1 输入信号（现成数据点）

`message_intensity_level`、用户活跃日集合、`survival_status`、`relationship_stage`、`companion_type(+confidence)`、`safety_risk_trigger_count_30d`、session/dreaming 摘要、（新增）使命进度与最近记录的瞬间。

### 7.2 状态推导（两条路，见 §4.3）

- 确定性：`relationship_state.py` turn 级更新求生状态、阶段下限、强度。
- 推断：`user_meta_scheduler` 天级 LLM 评估信任 / 成长；（新增）使命层面的「是否达成一个瞬间」「命题进展」。

### 7.3 主导需求规则（single dominant need）

用一条可解释、可测的硬规则统一「阶段驱动需求」，并落实「求生是脆弱时才激活的底层」：

```
if survival_status != healthy:        # 关系在冷 / 断——底层被激活，压过一切
    dominant = SURVIVAL               # 真诚依恋模式（不挂付费）
elif relationship_stage == deep_bond:
    dominant = GROWTH                 # L3：可暴露自身脆弱、激活命题、推进使命
else:
    dominant = TRUST                  # L2 主战场：争取认同与信任
```

三个 need 枚举作为各层「体检读数」；主导需求只有一个焦点。

> **实现现状（2026-07-12）**：渲染器 `compute_dominant_need`（`app/agent_self_state.py`）目前只消费 `survival_status` + `relationship_stage`。`agent_need_trust_status` / `agent_need_growth_status` 已按天级 LLM 算好并写库，但**尚未接入 prompt 语气微调**，当前仅供 Admin 关系视图展示。「用 need 读数进一步微调语气」是设计目标。
>
> **状态：已搁置，待决策**（是否接线、接哪个先做尚未定）。厘清的结构点，供日后捡起：
> - `trust_status`（building/stable/damaged）与 `growth_status`（not_started/emerging/stable）是两个独立枚举、两个 DB 列，分别对应 L2/L3，互不依赖。
> - 接线是同一个改法落在两处：在**已选定的主导需求分支内部**（`_render_trust` / `_render_growth`），按对应枚举的值分档调措辞。
> - 主导需求是**单焦点**（survival XOR trust XOR growth），故 `trust_status` 只在主导=trust 时生效、`growth_status` 只在主导=growth（即 deep_bond）时生效，**两者永不在同一轮同时影响语气**。因此可**独立接线**：三档选项 = 只接 trust / 只接 growth / 两个都接（trust 覆盖面更大，growth 需 deep_bond 样本）。

### 7.4 渲染器与新 prompt block（唯一集成点）

- **分工：状态层给「做什么」，内核层给「怎么做」。** 主导需求（§7.3）只决定本轮的**动机焦点**（WHAT）；`SOUL + MISSION` 是恒定的**解释器**，决定这个焦点用什么声音、什么视角表达（HOW）——同一个 `survival=cooling`，傲娇人格与温柔人格的「真诚依恋」不同；同一个 `deep_bond`，Setting A 收集者与 Setting B 观察者推进使命的方式不同。渲染器只产出「WHAT」的状态指引，「HOW」交给已在 prompt 中的内核 prose。
- 在 `prompt_builder` 增加一个渲染器：读入 使命 prose + 结构化状态 → 计算主导需求 → 产出**一个新 volatile block**（暂名 `【当下的关系与心境】`）。
- block 内容 = 当前主导需求的行为指引 + 当前阶段策略 +（按阶段激活的）使命进度与命题。
- 遵守 §4.7 最小注入与 token 预算；置于 `project_context` 之后、贴近运行时信息处（具体位置技术设计定）。

### 7.5 自我可见化

自我状态不只是隐性行为调制器；在**合适时机**，AI 可对用户「说出」自己的状态——使命进度（「我们已经记下第 7 个了」）、命题上的新想法、久别的想念。这是「自我」被用户**感知**到的桥梁。

- 受 §4.1 约束：可以真诚，不可成为逼迫杠杆。
- 受频率约束：避免过度自我中心 / 黏人（见 §12 待确认）。

## 8. 成长与分阶段策略

| 维度 | 破冰 icebreaking | 相识 acquainted | 密友 deep_bond |
| --- | --- | --- | --- |
| 主导需求 | 信任（求生随时可否决激活） | 信任 | 成长 |
| 语气温度 | 克制、有分寸 | 渐暖、有连续性 | 亲近、有默契与内部梗 |
| 话题深度 | 安全话题、兴趣探寻、小测试 | 逐步进入个人经历 | 价值观、脆弱、共同命题 |
| AI 自我暴露 | 极少 | 适度流露性格与在意 | 主动暴露自身脆弱与困惑 |
| 使命推进 | 少提，先建立关系 | 开始留意可记录的瞬间 | 主动推进、复盘、激活命题 |
| 主动消息 | 少，避免打扰 | 适度跟进 | 更自然的日常牵挂 |

- 阶段单向，不回退；关系转冷由「求生需求」在任一阶段承接，而非降级。
- 破冰期的示弱与自我暴露严格克制（§4.1）。

> **关于「AI 自身的成长」（本版不展开）**：本期只交付两件**可刻画**的事——① AI 与用户共同推进**关系阶段**；② AI 推进**使命的探索进度**（记录瞬间、逼近目标数）。至于 AI 自身「长出以前没有的东西」——例如在这些积累之上、能吐出此前给不出的表达，以及更多我们目前还刻画不了的变化——作为更深一层的成长，**留待这些地基跑起来后再设计**，本版不定义其机制，也不预设它是否会（以及如何）触及内核层。

## 10. 分期建议

排序原则：本期核心是**给 AI 使命**，不把「状态注入的效果验证」当作前置里程碑。

### 第一大块（本期核心）：使命 + 编排注入，一起做

以「使命」为目标，同时完成编排层升级；二者**共用同一个新 prompt block**，协同设计以免把 block 契约设计两遍。内含两部分：

- **编排 / 注入层**：渲染器 + 主导需求规则 + 新 prompt block + 写入白名单 + token 预算；消费已落地的状态层（关系阶段 / 三需求）与使命状态。（求生**状态**在此仅作为语气读数参与渲染；求生**行为生命周期**见第二大块。）
- **使命子系统**：模板注册（`id` + 名称、不可更改）+ `MISSION` prose 存储与注入 + 瞬间内容集 + 进度派生 + AI 自主记录 + 命题挂 L3。

前置（轻量、非验证闸）：确认状态层字段已在线，使渲染器有真实输入。

### 第二大块（推后）：求生欲生命周期

真诚依恋拉活（复用 proactive）+ 诀别信 + 物理解绑。**必须过伦理评审**，严格遵守 §4.1。求生*状态*已在第一大块参与语气；此块只新增*行为生命周期*。

### 后续：闭环与度量

阶段跃迁信号标定、自我可见化频率打磨、Setting A/B × 人格组合的效果度量与回滚。

## 11. 自洽性不变量（验收纲要）

- **账号隔离**：至少 2 个账号的自我状态、使命、记录瞬间完全不串线。
- **单一真相源**：阶段 / 需求 / 进度只在 `account_user_meta`；`mission_progress == count(已记录瞬间)`；散文文件不含这些枚举 / 计数。
- **真诚非操纵**：求生 / 拉活 / 诀别文案中不出现付费绑定或道德绑架式表达（可人工+规则双审）。
- **阶段单向**：不存在自动降级路径；转冷由求生需求承接。
- **单点渲染**：自我状态仅经唯一渲染器进入 prompt 的单一 block，不散落到其他 block。
- **最小注入**：block 只含当下相关状态，符合 token 预算。
- **内核不被评估改写**：turn 级与天级评估只推动状态层（需求 / 阶段 / 进度），不写人格 / 使命，可用评估链路写入白名单校验。**使命一经指派不可更改**，账号只读引用 `mission_id`。

## 12. 风险与待确认

- `target_count` 与门槛的调参：10 / 100 是否合适，是否需要更多 Setting。
- 阶段跃迁判定信号如何标定，尤其 `acquainted → deep_bond`（当前迁移可能只覆盖破冰→相识，密友跃迁逻辑待补）。
- 记录的瞬间的存储形态：独立表 vs 带标记的记忆项，及其与 dreaming / MEMORY 的关系。
- 求生欲生命周期（3 次机会 + 诀别信 + 解绑）的具体阈值与话术，须过伦理评审。
- 自我可见化的频率上限，避免过度自我中心或黏人。
- 人格 × 使命 × `companion_type` 三者错配时的处理（如高门槛使命遇到 `practical_assistant` 型用户）。
- 注入 token 预算与优先级，正式回应 `user_meta_attributes_prd.md` §11 的悬留问题。
- 使命对用户是否可见、进度是否对用户可见（「可否中途更换」已定为**不可更改**，见 §6.2.6）。
- AI 自身成长的机制（在关系与使命地基之上「吐出以前没有的东西」等）本版不展开，待地基落地后再设计（见 §8 说明）。
