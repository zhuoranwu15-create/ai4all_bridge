# 主动消息送达窗口对齐

> 临时跟踪文档，用于团队同步"微信 24 小时送达窗口"这件事对主动消息子系统的影响、已确认的决策与开发跟进。
> 收口后可归档到 `docs/archive/`。产品级结论沉淀在 [`proactive_prd.md` §9](../product/proactive_prd.md)，技术根因沉淀在
> [`weixin_context_token_send_semantics.md`](../troubleshooting/weixin_context_token_send_semantics.md)，本文档只承载
> "接下来要做什么、做到哪了"。

## 背景

微信个人号给某个联系人发主动消息，能否送达取决于该联系人与我们之间的会话凭证（`context_token`）是否新鲜；这个凭证只由
联系人自己发来的入站消息刷新。联系人沉默超过**24 小时**（官方口径，2026-07-08 经自测+网络搜索确认；内部探针数据
20h45m 成功/44h45m 失败与此吻合），凭证过期后微信的 iLink 网关会静默拒收，我方之前会误判为发送成功。完整技术排查见
[`weixin_context_token_send_semantics.md`](../troubleshooting/weixin_context_token_send_semantics.md)；2026-07-03 已完成一次
可观测性修复（把 iLink 的 `ret`/`errcode` 透传回 ai4all，静默丢失从"误判成功"变成"显式失败"），但这个修复目前只是手术式
打在 aliyun1 一台机器运行中的 dist 上，尚未固化为正式补丁，aliyun2 是否已打未经确认——这部分的固化跟踪在
[`openclaw_patches_maintenance.md` §2.7](../tech_design/openclaw_patches_maintenance.md) 的 TODO 里，本文档不重复。

## 已确认的决策（2026-07-08）

1. **不复用 `accounts.status` 表达"暂不可触达"**。`status` 是账号级终止状态，覆盖运营禁用**和用户主动注销**两种场景，
   语义上和"因用户沉默导致微信暂时拒收"完全不同；且 `policy.py` 的账号状态检查排在提醒等豁免分类之前，混用会连
   "必达"的用户提醒都一起拦住。
2. **新增独立的可触达性判断，统一走一个函数** `get_account_touch_state(account_id, now)`。只读
   `channel_bindings.last_seen_at`（已确认只在真实入站消息时刷新，可靠信号），现算现返回 `reachable`/`stale`，
   不新增存量字段、不需要迁移、不需要定时任务翻转状态。**业务代码一律走这个函数**，不允许各处自己拼日期比较。
3. **陪伴跟进 / 内容邀请 / 拉活（hot_topic）等非豁免分类**：`touch_state == "stale"` 时直接不生成候选、不发送。
4. **提醒 / 承诺创建时，system prompt 提示用户保持互动**——已完成，见下方进度看板 P0。
5. **【2026-07-08 反转】用户提醒 / 承诺：`touch_state == "stale"` 时改为不再触发**，不再"照常尝试发送 + 靠显式
   失败机制记录"（原决策 5 的做法）。产品侧判断：过了 24 小时送达窗口的提醒/承诺已经过时效，尝试发送既送不到，
   还占用一次网关调用和 attempts 计数，不如直接不触发。一次性提醒直接终态 `cancelled`（`error=proactive_touch_stale`）；
   周期提醒（`recur_rule`）只跳过本次，正常推进到下一周期，序列不中断。承诺没有周期概念，同一次性提醒终态处理。
   见下方 P2 详情。用户此前是否被提前告知（system prompt 里"保持联系"的提示，见决策 4）仍然生效，作为事前预期管理；
   事后是否告知用户"有条提醒因为太久没聊天没发出去"折进 P3（范围见下方 P3 详情）。

## P1 详情：`get_account_touch_state()`（✅ 已实现）

- 位置：`app/proactive/delivery/touch_state.py`（新模块），DB 查询落在 `app/db/accounts.py::get_account_last_inbound_at`
  （`SELECT MAX(last_seen_at) FROM channel_bindings WHERE account_id = ?`，走既有
  `ix_channel_bindings_account_seen` 索引，无新迁移）。
- 签名：`get_account_touch_state(*, account_id: str, now: Optional[datetime] = None) -> Literal["reachable", "stale"]`。
- 判定：`now`（默认 `beijing_naive_now()`，内部会剥掉 tzinfo 以兼容传入 tz-aware 值的调用方，比如 admin
  run-once 用的是 `beijing_now()`）与 `last_inbound_at` 相差超过 `WECHAT_TOUCH_WINDOW_HOURS = 24`（模块级常量，
  不是 settings 配置项）判定为 `stale`；账号没有任何 `channel_bindings` 记录时同样判 `stale`。
- **2026-07-08 简化决定**：最初实现留了 20（后调到 22）小时的"操作缓冲"，怕时钟误差/处理延迟导致刚好卡在
  窗口边缘的发送失败。后来产品侧确认 24 小时是官方口径的确切事实，于是决定去掉缓冲——缓冲的代价是把本来
  能送达的候选提前当作 stale 放弃、白白浪费发送机会，而 24h 这个数字本身已经不是靠猜的了。因此把配置项
  `proactive_touch_stale_after_hours` 从 `app/config.py`/`tests/conftest.py` 整个删掉，改成 `touch_state.py`
  里的一个简单模块常量，函数内部也去掉了原来的 `try/except float(...)` 防御性解析（常量不需要）。
- 单测：`tests/test_proactive_touch_state.py`（7 例：无 binding、窗口内、超窗口、多 binding 取最新、tz-aware
  `now`、24h 边界两侧各一例）。因为不再读 settings，`conftest.py` 里对应的 per-module patch 行也一并删除了。

## P2 详情：接线点（✅ 已实现）

- `app/proactive/recall/topic_followup.py`、`content_invitation.py`、`hot_topic.py`、`manual_companion.py`：均在
  `account.get("status") != "active"` 检查之后加了 `get_account_touch_state(...) == STALE` 判断，命中时
  `_no_op(reason="proactive_touch_stale")`，不生成候选（不进 LLM 调用，省 token）。
- `app/proactive/delivery/policy.py`：**暂未加**。当前这四个 recall 模块是非豁免分类候选生成的唯一入口，闭合
  候选生成层等价于闭合发送——如果未来出现绕过候选生成层直接进 `dispatch_proactive_text` 的非豁免路径，需要回来
  在 `evaluate_outbound_policy` 补一道 `proactive_touch_stale` blocked reason。
- **【2026-07-08 反转决策 5】** `app/proactive/obligations/reminders.py::dispatch_reminder`、
  `commitments.py::dispatch_commitment`：在 `claim_due_reminder`/`claim_due_proactive_commitment` 成功、真正
  `dispatch_proactive_text` 之前加了 `get_account_touch_state(...) == STALE` 判断，命中时不触发：
  - 一次性提醒 / 承诺：直接终态 `cancelled`（复用既有 `cancel_reminder`/`cancel_proactive_commitment`，
    `error="proactive_touch_stale"`，不新增状态值）。
  - 周期提醒（`recur_rule` 非空）：只跳过本次，新增 `app/db/proactive.py::reschedule_reminder_stale_touch`
    把 `due_at` 推进到下一周期、状态回退 `pending`，不计入 `sent_count`/`last_sent_at`（因为没有真的发送），序列
    不中断。
  - `dispatch_reminder`/`dispatch_commitment` 返回 `{"status": "skipped", "reason": "proactive_touch_stale", ...}`，
    与既有"未到期"跳过分支同族。
  - 承诺此前经 `companion_followup` 分类走 `evaluate_outbound_policy`（非豁免），但因为绕过了 P2 阻断的候选生成层
    （承诺不经 4 个 recall 模块，直接从 obligations 层触发），touch_state 检查此前是空档——这正是 P2 详情里提到的
    "未来出现绕过候选生成层的路径"，本次一并补上。

## P3 详情：提醒/承诺过期告知机制（设计未定，待讨论）

**范围已缩小（2026-07-08）**：由于决策 5 已反转（P2 现在直接不触发 stale 的提醒/承诺，而不是"尝试发送 + 记录失败"），
P3 不再是"补发机制"，而是"事后告知机制"——被 `proactive_touch_stale` 跳过的提醒/承诺，让用户在下次开口时知道
"之前有条提醒因为太久没聊天没发出去"，而不是尝试重新发送（重发也送不到，因为送达窗口的判断标准不会变）。

这个范围收窄也顺带解决了此前悬而未决的 `ret:-2` 语义问题：`ret:-2`（真限速 vs 陈旧 token 拒收，见 troubleshooting
文档 §5 最后一条）是网关**尝试发送后**才会遇到的歧义；P3 现在处理的是**从未尝试发送**、有清晰 `error=proactive_touch_stale`
标记的记录，不再需要判断失败原因，`ret:-2` 的精确语义澄清完全独立于 P3，折进 P4 单独评估（是否值得再打诊断补丁，
用于系统级限速告警），见下方 P4 详情。

需要回答的问题：

- 触发时机：用户下次入站时（`turn_service.py` 的 inbound 处理路径，`upsert_channel_binding` 刷新 `last_seen_at`
  之后）检查该账号近期是否有 `error="proactive_touch_stale"` 的终态提醒/承诺。
- 告知几条、超过多久不再告知（避免堆积很久以前的旧提醒都翻出来说一遍）、怎么自然带出"之前有条消息没发出去"
  （避免生硬的"发送失败"措辞，呼应决策 4 的话术风格）。
- 是否需要同步更新 `docs/product/proactive_prd.md` §10 的验收标准。
