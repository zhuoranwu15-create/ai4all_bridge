# 主动消息（app/proactive/）重构对齐

> 临时跟踪文档，用于团队同步主动消息这块的代码重构进度、决策与 bug 状态。
> 阶段1 完成、整理稳定后可归档到 `docs/archive/`。
> 完整设计见各阶段下文；原始评审结论由本文档承载，无需翻聊天记录。

## 背景

`app/proactive/`（13 文件 / ~4400 行）承载主动消息全部业务：**生成候选 → 策略闸门 → 出站发送**。
评审发现两类问题：

- **结构**：`account_checks.py`(950) / `reactivation.py`(904) 是 god-file；4 段 system prompt 内联在业务代码；
  编排器 `scan_due_proactive_account_checks` 错放在 `state.py`；"候选"概念有 5 种存法。
- **正确性 bug B**：reactivation 自身 avoidance 窗口（60min）与 policy 对 companion_followup 的 avoidance 窗口（6h）
  口径不一致，候选被 policy 取消后既不清也不改期 → 每 tick 空转、卡到次日。

## 总体策略（已确认）

- **深度 = 外科式整理**：行为零变更，旧模块路径做"门面再导出"，对外 import 全部不变。
- **顺序 = 阶段0 先单独修 bug（独立 PR）→ 阶段1 结构整理（独立 PR）**。
- **account_check 休眠路径 = 保持 admin-only，仅补文档**（产品有意设计，零行为变更）。
- 不引入新依赖；账号隔离不变量不受影响。

## 阶段0 详情

### 0.1 bug B — reactivation 候选被 policy 取消后空转
- **根因**：`dispatch_reactivation_candidate`（`reactivation.py`）只在 `sent` 时清候选；`cancelled` 既不清也不改期，
  `scheduled_at` 停在过去 → 每 tick 重复评估 + 重跑 policy；planning 见 pending 候选不重规划 → 卡到次日。
- **修复**：给 `outbound_status == "cancelled"` 加显式分支——`_next_slot_after` 有下一 slot → `reschedule`（reason
  `send_blocked_policy`）返回 `delayed`；无 slot → `clear`（reason `send_blocked_policy_final_slot`）返回 send_blocked。
  把每-tick 空转降为每-slot 重试（无窗口下当天最多 3 次后清除，等下次 planning 重新生成）。
- **不动**：policy、`_avoidance_count` 口径（两 knob 语义不同，刻意保留）；`failed` 等其它状态维持原 `send_blocked` 行为。
- **测试**：`tests/test_reactivation.py` 新增——policy 取消时断言 `delayed` + `scheduled_at` 前移、第二 tick 不再立即 due；末位 slot 时断言候选清除。
- **已知次要遗留**：当账号设了 allowed_windows 时 `_next_slot_after` 恒返回未来 slot（不返回 None），若 policy 永久拦截
  （如 master 关闭）候选不会经此路径清除，只会被每 slot 重试一次——仍远好于每 tick；彻底清理留作后续。

### 0.2 bug A — account_check 休眠路径（仅文档）
- **结论**：account_check candidate **仅由 admin 端点** promote 产生（`admin_proactive.py`），自动调度不生成，
  故 scheduler 的 account_checks 步在无人工候选时恒 `no_op`。这是有意设计。
- **动作**：`scan_due_proactive_account_checks` 与 `account_checks.py` 模块 docstring 各加一句说明。零行为变更。

## 阶段2 详情 — 推荐器 seam（自主外联族，行为等价）

### 决策（已确认 · 第二轮）
- **覆盖范围 = 仅自主外联族**：`topic_followup` / `content_invitation` / （admin）`manual_companion` 走"召回→排序→选择"；
  `reminder` / `commitment` 属"义务型"，时间锚定直发，**不纳入**。
- **全局召回 = 协议先到位、实现留 stub**（Q1）：`Recaller` 协议本轮带上 `scope=account|global` 维度；真正的全局
  recaller（如热点话题扇出+跨用户去重）**需跨账号候选池，等阶段3 表落地再接**。本轮不建表、行为等价。
- **account_check = 更名归位、仍 admin-only**（Q2）：消除"一个词背三件事"的语义混乱，零行为/产品变更。
- **存储层 = 本轮按职责重切 + 门面**（Q3）：`reactivation.py` 拆成 store/scheduling/dispatch 三层职责，退为门面；
  对外 `from app.proactive.reactivation import …` 全不变。`reactivation` 退回为"候选 kind 分组 + 产品目标"，不再当层名。
- 仍**不建候选池表**；账号隔离不变量不受影响。确立"召回 ↔ 选择 ↔ 存储 ↔ 调度 ↔ 派发 ↔ 发送"全切割面，
  为阶段3（`proactive_candidates` 表 + 真·全局召回）/ 阶段4（真实排序信号 + 生成拆进程/仓）打地基。

### 现状基线（要形式化的"隐式选择"）
`plan_reactivation_candidate`（`reactivation.py:410`）= 固定优先级选择器：topic_followup 命中即用（优先级1），
否则 content_invitation（`action=="content_invitation_candidate_created"`，优先级2），都空 → no_op
（reason = `content_result.reason or topic_result.reason or "no_reactivation_candidate"`）。

### 改动清单（行为等价 · 门面再导出保住对外路径）

**A. 选择层 selection/（新增，纯模块）**
- `selection/__init__.py`、`selection/candidate.py`：`ProactiveCandidate` dataclass（account_id / kind / scope /
  topic / text / payload / **features**(排序信号位，本轮空) / scheduled_slot / scheduled_at / dedupe_key /
  expires_at / source / confidence / metadata）+ `from_legacy` / `to_legacy`，与现有候选 dict **双向 round-trip**。
- `selection/ranker.py`：`DISCRETIONARY_RANK = ("topic_followup", "content_invitation")` + `rank_index`；纯数据。
- `selection/selector.py`：`select_first(ranked_kinds, proposers) -> (chosen_kind, candidate, outcomes)`；纯机制，
  **零 proactive 依赖**，杜绝循环。

**B. 召回协议 generation/base.py（新增）**
- `Recaller` Protocol：`kind: str`、`scope: Literal["account","global"]`、`propose(ctx) -> list[ProactiveCandidate]`。
  **薄协议，不上胖基类**（content_invitation 用 tools，与 completion 形态不共骨架）。
- topic_followup / content_invitation 暴露 account-scope 的 propose 适配器（包既有 `generate_*`，函数本身不动 →
  既有 `patch("…generation.topic_followup.generate_completion")` 等 patch 点不变）。全局 recaller 本轮不建（stub）。

**C. account_check 更名归位（Q2，仅 app/proactive 内，行为等价）**
- `generation/account_check.py` → `generation/manual_companion.py`；Python 符号/docstring 改诚实名
  （admin 手工 companion，自动链路不生成）。
- planning 编排器 `scan_due_proactive_account_checks` 的 docstring/局部命名澄清其"规划全部自主外联候选"语义。
- **明确不动（避免越界 + 数据迁移）**：DB 持久化 key 串 `"account_check_candidate"`、`app.db` 的
  `*_account_check_*` 函数名、`DEFAULT_ACCOUNT_CHECK_INTERVAL_SECONDS` / `planning_interval_seconds`、dispatch
  source 串 `"account_check"`、`scan_due_proactive_account_checks` 这个**对外函数名**（仍由门面/state 再导出，测试无感）。
  → 本轮只清"模块与符号语义"，不动跨层契约与已落库的字符串。

**D. 存储层按职责重切（Q3，门面再导出）**
- `reactivation.py` 拆为：
  - `candidate_store.py`：候选持久化 + 去重规则（`normalize/get/upsert/clear/reschedule_reactivation_candidate`、
    `get_reactivation_candidate_from_metadata`、`reactivation_outbound_metadata`、`rule_reactivation_dedupe_check`、
    `_avoidance_count` / `_inbound_count_after` / `_has_sent_reactivation_today`、`REACTIVATION_*` 常量）。
  - `scheduling.py`（由 `reactivation_slots.py` 更名）：slot/时间窗算法。
  - `dispatch/outreach.py`：`dispatch_reactivation_candidate`（含阶段0 的 cancelled 改期/清除）、
    `dispatch_due_reactivation_candidates`、`_candidate_from_content_invitation`。
- `reactivation.py` 退为**门面**，再导出上述全部公共符号 + `next_reactivation_slot` 等，对外路径逐一不变
  （核对阶段1 门面符号清单）。

**E. plan 适配器（2.7）**
- `plan_reactivation_candidate`（落 `dispatch/outreach.py` 或 `selection/`，门面再导出）改为"组装 proposers →
  `select_first` → `upsert` → 拼回原 dict"，**签名与返回 dict 逐键不变**。

### 行为等价义务（自审清单）
- 顺序：topic 先于 content（rank 元组）；topic/content 命中条件、no_op reason 回退链、被抢占时
  `topic_followup_candidate_selected` no_op，逐键对齐原实现。
- 存储：仍 `upsert_reactivation_candidate` + `_with_default_schedule`，metadata key 与 schedule 不变。
- 门面：对 1.2/2.6 列出的每个公共符号 `python -c "from app.proactive.<旧模块> import <符号>"` 全通过。

### 测试
- 新增 `tests/test_proactive_selection.py`：ranker 顺序、selector first-hit/全空、`ProactiveCandidate` round-trip、
  `Recaller` propose 契约。
- 既有 `test_reactivation.py` / `test_account_checks.py` / `test_admin_proactive_state.py` / `test_proactive_scheduler.py`
  **尽量不改且全绿** = 行为等价证明（若仅因模块迁移需改 `patch` 目标，按"patch where it's used"最小调整，逻辑断言不动）。
- conftest：selection 三模块纯净不读 settings，无需新增 patch；`generation/manual_companion`、新 dispatch/store 模块若
  `from app.config import settings`，按 per-module 约定在 conftest 两 fixture 补 patch 行。
